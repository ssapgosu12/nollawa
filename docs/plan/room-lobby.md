# 방 흐름과 방 로비

**무엇에 대한 문서인가**: 메인 화면 → 방 로비 → 게임 목록으로 이어지는 화면 흐름, 방 코드 규격,
방장 권한과 준비 규칙. 게임 규칙은 이 문서에 없다(게임별 문서를 본다).

**원문**: `docs/spec/DIRECTIVES.md` D-001. 아래 내용과 원문이 어긋나면 원문이 이긴다.
**전역 제약**: `docs/PLAN.md` §5 색 · §6 화면 규칙 · §11 구조 예산. 이 문서가 그것을 덮어쓰지 않는다.

각 항목은 **[원문]**(사용자가 지정) 또는 **[도출]**(그 지시에서 계획이 끌어낸 것)로 표시한다.
[도출]은 사용자 승인 없이 뒤집을 수 있고, [원문]은 뒤집을 수 없다.

---

## 1. 화면 흐름

```
[이름]  최초 1회만. 기기에 저장되고 서버에 남지 않는다. 언제든 바꾼다.
   │
[메인]  ┌ 이 기기에서 플레이 ──────────────→ [게임 목록]   (방 로비를 건너뛴다)
        ├ 방 참여  [ABC-67] ───┐
        └ 방 생성 ─────────────┴─────────→ [방 로비]
                                              │
                                       게임 변경 ↕ (방장만 선택 가능)
                                              │
                                          [게임 목록]
                                              │
                                    플레이 시작(방장) → [대국]
```

- [원문] 메인 화면의 버튼은 **이 기기에서 플레이 · 방 참여 · 방 생성** 셋이다.
- [원문] **이 기기에서 플레이를 누르면 곧장 게임 목록**으로 간다. 방 로비를 거치지 않는다.
- [원문] **방 참여와 방 생성은 방 로비**로 간다.
- [도출] 이름 입력은 최초 1회로 남는다(기존 §4). 두 번째 실행부터 메인 화면이 첫 화면이다.
- [도출] 화면 흐름에서 로비를 건너뛰는 것이지 **코드 경로가 갈라지는 것이 아니다.** 통신 계층
  (`Transport`)에 자기 자신에게 되돌려 주는 구현을 두어 로컬·원격이 같은 경로를 타는 기존 설계를
  유지한다. 로비 코드가 두 벌로 갈라지는 것을 막기 위한 것이고, 이 원칙은 바뀌지 않았다.

## 2. 방 로비 화면

세로 배분은 `100svh` 기준이다(`dvh` 금지 — `PLAN.md` §6).

```
┌──────────────────────────────────┐
│           ABC-67                 │  최상단 · 방 코드 · 큼지막하게
├──────────────────────────────────┤
│  텍사스 홀덤            2~6명    │  약 20% · 현재 게임 카드
│  #파티  #베팅  #숨긴정보   (…)   │  (…) = 게임 설정 변경
├──────────────────────────────────┤
│  ┌────────┐  ┌────────┐          │  약 60% · 2×3 격자 (최대 6인)
│  │👑 나    │  │  민수   │        │  왕관 = 방장
│  │  준비   │  │  준비   │  (…)   │  (…) = 방장에게만 보이는 유저 메뉴
│  ├────────┤  ├────────┤          │
│  │  지원   │  │ (빈자리)│        │
│  │  대기   │  │         │        │
│  ├────────┤  ├────────┤          │
│  │(빈자리) │  │(빈자리) │        │
│  └────────┘  └────────┘          │
├──────────────────────────────────┤
│  [게임 변경]   [플레이 시작]     │  최하단
│              3/4 준비됨          │
└──────────────────────────────────┘
```

- [원문] **방 코드는 최상단에 큼지막하게.**
- [원문] **상단 약 20%에 현재 게임** — 게임 제목, 플레이 인원수, 태그(파티·협동 등).
- [원문] 게임 카드 **오른쪽에 `(…)` 버튼** — 누르면 **게임 설정 변경**. 텍사스 홀덤 예: 시작 크레딧,
  최대 베팅 가능 크레딧, 올인 허용 여부.
- [원문] **아래쪽 약 60%에 2×3 격자**로 현재 플레이어. **방을 만든 사람에게 왕관 표시**(방장).
- [원문] **사람들 옆에 현재 준비 상태**가 나온다.
- [원문] **최하단에 플레이 시작 버튼**, 그 **왼쪽에 게임 변경 버튼**, 그리고 **준비된 인원수**
  (예: 방에 4명이고 3명이 준비했으면 `3/4 준비됨`).
- [도출] 2×3은 **세로 화면에서 2열 3행**, 가로가 넓은 태블릿에서는 3열 2행으로 눕힌다. 칸 수 6은
  한 방 최대 인원 6인과 같다(`PLAN.md` §0 규모 전제).
- [도출] 나머지 약 20%는 최상단 방 코드 줄과 최하단 버튼 줄이 나눠 갖는다. 20/60은 **고정 비율이
  아니라 목표 비율**이다 — 작은 폰에서 버튼이 잘리면 안 되므로 격자가 먼저 줄어든다(`PLAN.md` §6
  화면 잘림 금지가 상위 규칙).

## 3. 권한 — 방장과 그 외

| 기능 | 방장 | 그 외 |
|---|---|---|
| 플레이 시작 | 누를 수 있다 | **비활성** |
| 게임 변경 | 목록을 보고 **고를 수 있다** | 목록을 **볼 수만** 있고 고르지 못한다 |
| 게임 설정 변경 `(…)` | [도출] 할 수 있다 | [도출] 값만 보인다 |
| 유저 카드 `(…)` 메뉴 | 보인다 — **추방 · 방장으로 승격** 등 | 보이지 않는다 |
| 준비 상태 토글 | ↓ OPEN-1 | 누를 수 있다 |

- [원문] 방장이 아니면 **플레이 시작 버튼이 비활성화**된다.
- [원문] 방장이 아니면 게임 변경에서 **목록만 볼 수 있고 선택은 안 된다.**
- [원문] 방장에게만 각 유저 카드 옆 `(…)` 메뉴가 있고, 누르면 **팝업으로 추방·방장 승격** 등이 뜬다.
- [도출] 게임 설정 변경도 방장 권한으로 둔다 — 게임 선택이 방장 권한인데 그 게임의 규칙 옵션만
  누구나 바꿀 수 있으면 앞의 제한이 무의미해진다.

## 4. 시작 조건 — 준비 인원

[원문] 방 인원별로 필요한 준비 인원:

| 방 인원 | 시작에 필요한 준비 인원 |
|---|---|
| 2명 | **2명** |
| 3명 | **2명** |
| 4명 | **3명** |
| 5명 | **3명** |
| 6명 | **4명** |

- [도출] 이 표는 **⌊n/2⌋+1**(과반)과 정확히 일치한다. 구현은 표를 하드코딩해도 되고 식을 써도
  되지만, **표가 정본이다** — 나중에 사용자가 한 칸만 바꾸면 식은 깨진다.
- [도출] 조건을 못 채우면 플레이 시작 버튼은 비활성이고, 방장이 눌러도 시작되지 않는다.
- [도출] `3/4 준비됨`의 분모는 **방 인원**이지 필요 준비 인원이 아니다(원문 예시가 4명 방에서 `/4`).

## 5. 방 코드 규격 (기존 §4에서 이관 · 확정)

**`ABC-67` — 영문 3자 + 하이픈 + 숫자 2자.**

- 영문은 **대소문자 구분 없음**(입력 즉시 대문자로 정규화). **`I` · `L` · `O`를 뺀 23자**만 쓴다 —
  각각 `1` · `1` · `0`과 혼동되기 때문이다.
- 숫자는 0~9 전부. **글자 자리와 숫자 자리가 위치로 분리돼 있어** `0`/`O` 혼동이 생기지 않는다.
- 총 경우의 수 **23³ × 10² = 1,216,700개.**

| 확인 항목 | 결과 |
|---|---|
| 동시 방 20개일 때 코드 충돌 확률 | 0.0164% |
| 동시 방 100개일 때 | 0.4109% |
| 무작위 추측이 활성 방에 걸릴 확률(동시 20개) | 0.00164% |
| 10% 확률로 남의 방을 맞히는 데 필요한 시도 | 약 6,400회 |

월 이용자 30~300명 규모에서 충돌·추측 모두 실질 문제가 아니다. 다만 둘은 반드시 넣는다:

1. **생성 시 중복 검사.** 릴레이가 방 코드를 그대로 Durable Object 이름으로 쓰므로(`idFromName`),
   같은 코드가 두 번 나오면 **서로 모르는 두 무리가 같은 방에 들어간다.** (M0-FIX에서 구현 완료)
2. **금칙 조합 차단.** 3글자 조합 12,167개에는 불쾌한 것이 섞인다. 단톡방에 붙여 넣는 코드이므로
   수십 개짜리 블록리스트를 둔다. **상표 금칙어 게이트와 같은 파일에 두지 않는다** — 목적이 다르다.

**입력 UI**: 한 칸짜리 텍스트 입력에 `autocapitalize="characters"`, 3자 입력 시 하이픈 자동 삽입,
허용 문자가 아닌 입력은 무시. **숫자 자판을 강제로 띄우지 않는다**(앞 3자가 문자라 전환이 번거롭다).
공유 주소는 `#/r/ABC-67` 형태로 하이픈을 그대로 쓴다.

## 6. 게임 목록 (기존 §4에서 이관)

- **인원 구분 3개**: 1인 / 2인 / 3~4인. 방 인원이 정해져 있으면 **안 되는 게임은 흐리게 표시하되
  숨기지 않는다**(뭐가 있는지는 보여야 한다).
- **태그(다중 선택 시 좁혀짐)**: 봇 있음 · 대전 · 협동 · 동시진행 · 점수판 · 실물 필요 · 5분 이내 ·
  숨긴 정보.
- **검색**: 이름 + 별칭. 단 별칭 목록을 상표 grep 게이트의 예외로 두지 않는다 — 검색어는 사용자
  입력이지 우리 문자열이 아니므로, 코드에 상표를 넣지 않고 초성·유사어 매칭으로 처리한다.
- 게임 카드에는 **인원·소요 시간·태그**만 표시한다. 설명은 들어가서 본다.

## 7. 방이 게임보다 먼저 존재한다 (설계 근거 · 유지)

한 방에서 게임을 갈아 끼울 수 있다. 오목 한 판 두고 나가지 않고 바로 요트로 넘어간다. 매 판 방을
다시 만드는 기존 서비스 대비 실질 차별점이고, 리듀서 레지스트리 설계와도 맞는다. **게임 변경 버튼이
로비 최하단에 상시 있는 이유가 이것이다.**

## OPEN — 아직 정해지지 않은 것

착수 전에 사용자에게 물어야 한다. 임의로 정하고 구현하지 않는다.

- **OPEN-1 방장도 준비를 누르는가?** 원문의 "2명일 경우 2명 다"는 방장 포함으로 읽힌다. 그런데
  방장은 시작 버튼을 누르는 사람이라 준비가 중복일 수 있다. 두 안 — ⓐ 방장도 준비를 누른다(분모에
  포함) ⓑ 방장은 시작 버튼이 곧 준비다(분모에서 제외, 4명 방이면 `2/3 준비됨`).
- **OPEN-2 방장이 나가면 누가 방장이 되는가?** 남은 사람 중 가장 먼저 들어온 사람으로 자동 승계가
  기본값 후보. 아무도 없으면 방은 사라진다.
- **OPEN-3 게임을 바꾸면 준비 상태가 초기화되는가?** 다른 게임에 동의한 것이 아니므로 초기화가
  상식적이지만, 매번 다시 누르는 번거로움이 있다.
- **OPEN-4 정원이 게임보다 많으면 누가 두는가?** 방에 6명인데 사목은 2인 게임이다. 준비한 순서대로
  좌석을 채우고 나머지는 관전인지, 방장이 좌석을 지정하는지, 정원 초과면 시작을 막는지.
- **OPEN-5 빈 칸의 모습.** 6칸 중 비어 있는 칸을 "빈 자리"로 둘지, 방 코드를 복사하는 초대 버튼으로
  쓸지.
- **OPEN-6 "이 기기에서 플레이"의 게임 설정 변경은 어디서 하는가?** 로비를 건너뛰므로 `(…)` 버튼이
  놓일 자리가 없다. 게임 목록의 카드에 두거나, 게임 시작 직전 화면에 두어야 한다.
- **OPEN-7 판이 끝나면 어디로 돌아오는가?** 로비로 돌아와 다시 준비를 누르는지, 대국 화면에 남아
  "다시 시작"을 누르는지(현재 구현은 후자). 이 결정은 F1(다시 시작 전파)과 맞물린다.

## 구현 상태

| 항목 | 상태 |
|---|---|
| 메인 3버튼 흐름 | **미구현** — 현재는 이름 → 방 유형 → 게임 목록 |
| 방 로비 화면 전체 | **미구현** (`PLAN.md` §14 F4 = 이 화면의 최소판) |
| 방 코드 규격·중복 검사 | **구현 완료** (M0-FIX, 커밋 272505a) |
| 게임 목록 검색 | **부분** — 검색만 있고 인원 구분·태그 필터 없음 |
| 좌석 배정·준비 상태 | **미구현** — 티켓 M0-FEEDBACK이 좌석 배정만 먼저 넣는다 |
