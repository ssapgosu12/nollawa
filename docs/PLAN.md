## 0. 이 계획이 만드는 것

브라우저 주소 하나로 열리는 보드게임 모음. 설치·로그인·광고 없음.

| 모드 | 뜻 | 예 |
|---|---|---|
| **공용** | 기기 한 대를 여러 명이 같이 본다 | 마주 앉아 폰 하나로 오목 |
| **스플릿** | 기기 한 대의 화면을 나눠 각자 영역을 쓴다(한쪽은 180도 뒤집음) | 태블릿 놓고 요트 점수표를 좌우로 |
| **멀티** | 기기 여러 대. 방 코드를 공유해 붙는다. 매칭·랭킹·로그인 없음 | 각자 폰으로 함대 격침 |
| **점수판** | 실물 주사위·카드·보드로 놀고 앱은 기록만 한다 | 실물 요트 굴리고 점수만 앱에 |

**최상위 목표는 재미가 아니라 무유지보수다.** 1년을 방치해도 돌아가야 하고, 요금이 청구되지 않아야 하며, 고칠 사람이 없다는 전제로 모든 선택을 한다.

### 규모 전제 (설계 입력값)

**월 이용자 평균 30명, 최대 300명.** 상업 서비스가 아니라 **여행 가거나 친구들끼리 만났을 때 쓰는 개인적 목적**의 물건이다. 이 숫자가 설계 판단을 실제로 바꾸므로 명시한다.

무료 한도와 대조하면(Cloudflare 공식 문서 기준: 요청 10만/일, 실행시간 13,000 GB-s/일):

| | 최대(300명) | 평균(30명) | 무료 한도 |
|---|---:|---:|---:|
| 릴레이 요청 | 약 20,000/일 | 약 2,000/일 | **100,000/일** |
| 실행 시간 | 약 100초/일 | 약 10초/일 | 약 104,000초/일 상당 |

**한도의 20%와 0.1%다.** 이 규모에서는 **하이버네이션 구현이 틀려도 무료 한도가 버틴다**(방이 계속 깨어 있어도 하루 29 방-시간까지 여유). 따라서 "빈 방이 한도를 태운다"는 위험을 **치명 위험에서 위생 항목으로 강등**한다(§10). 방 상태를 storage에 넣는 규칙은 유지하되, 그 이유는 **비용이 아니라 "가끔 판이 초기화됨" 버그를 막기 위해서**다.

반대로 규모와 **무관하게 유지**되는 것들도 분명히 해 둔다 — 이용자가 1명이어도 똑같이 아픈 것들이다: iOS 저장 데이터 소실, 사용자가 옛 버전에 갇히는 문제, 상표 위험(오히려 소규모라 법적 대응 여력이 없어 더 중요), 1년 뒤 빌드 붕괴.

그리고 **"1년 방치"는 이 프로젝트의 최악의 경우가 아니라 정상 운영 상태다.** 몇 달 안 쓰다가 여행 가서 켜는 것이 기본 사용 패턴이다.

## 1. 확정 기술 스택

| 층 | 선택 | 한 줄 이유 |
|---|---|---|
| 언어·빌드 | TypeScript + Vite, **`dist/`(빌드 결과물)를 저장소에 커밋** | 진짜 위험은 실행이 아니라 "1년 뒤 다시 빌드가 되는가". 결과물을 커밋해 두면 빌드가 깨져도 사이트는 산다 |
| 화면 | **Preact 10** (약 5KB) | 2019년 이후 7년간 강제 이주 0회. 문법이 React의 부분집합이라 Codex가 가장 잘 쓰는 문법이 그대로 정답 |
| 보드 그리기 | **인라인 SVG**로 보드 전부 통일 | `viewBox` 하나로 폰·태블릿 크기 분기 코드가 0줄. 180도 회전에서도 터치 좌표 역산 불필요 |
| 스타일 | 손으로 쓴 CSS 500줄 이하, 리셋도 직접 | Tailwind·normalize가 자동으로 넣는 `-webkit-text-size-adjust:100%` 한 줄이 **안드로이드 글꼴 크기 설정을 죽인다** |
| 게임 엔진 | 순수 TS 리듀서 + 액션 로그. 공통 계약 5개, **공통층 820줄 예산** | 프레임워크를 모르는 순수 함수라 화면 기술을 갈아도 살아남는다 |
| 멀티 통신 | **Cloudflare Durable Objects WebSocket 릴레이** (§2) | QR 방식 재검증 후에도 유지 — 이유는 §2 |
| 권위 모델 | 좌석 권위 클라이언트 + 매 수마다 판 전체(약 1.5KB) 전송. **서버에 게임 규칙 없음** | 수 목록만 보내면 한쪽이 구버전일 때 에러 없이 두 화면이 갈라진다 |
| 정적 호스팅 | **Cloudflare Pages** 정본 + **GitHub Pages** 미러 (§7) | 둘 다 무료, 둘 다 카드가 걸리지 않는다 |
| 로컬 저장 | **IndexedDB** + `navigator.storage.persist()` + JSON 내보내기. localStorage 금지 | iOS Safari는 7일 미사용 시 localStorage를 지운다 |
| AI 상대 | 순수 TS + Web Worker, 타임아웃 + 탐욕 폴백 | Worker 로드가 조용히 실패하는 안드로이드 브라우저가 있고, iOS는 백그라운드 Worker를 죽인다 |
| 오프라인 | 직접 쓴 서비스워커 약 80줄. **무조건 즉시 적용 금지** — 배너 → 사용자 확인 → 새로고침 | 잘못 걸면 배포해도 사용자가 영원히 옛 버전을 본다 |
| 테스트 | Vitest + **체스 perft** + 레지스트리 전수 불변식 | 사람 리뷰어가 0명이라 기계 검증이 유일한 안전망 |

**의존성 상한 4개**(preact · vite · typescript · vitest). 항상 `npm ci --ignore-scripts`, 캐럿(`^`) 없는 정확 버전 고정.
※ 체스 단계의 `chess.js`는 5번째 후보 — 그 시점에 한 번 더 판단한다.

### APK: **만들지 않는다** (확정)

요구사항 중 웹이 못 하는 것이 하나도 없다. Google Play는 매년 target API 상향을 강제하므로 **Play에 올린 APK는 정의상 1년 방치가 불가능한 산출물**이다. 이 항목은 더 이상 미결이 아니다.

## 2. QR 코드 신호 방식 — 재검증 결과

**지적이 맞습니다. QR로 하면 중계 서버가 실제로 없어집니다.** 다만 조건이 붙고, 그 조건이 이 프로젝트의 용도와 어긋납니다.

### 어떻게 되는가

WebRTC(브라우저끼리 직접 연결하는 기술)로 연결하려면 두 기기가 접속 정보(SDP)를 주고받아야 한다. 보통은 이 교환을 서버가 중개하는데, **화면에 QR로 띄우고 상대가 카메라로 찍으면 서버 없이 교환된다.** 실제 구현체가 여럿 있다(2014년 데모부터 2026년 QWBP 프로토콜까지).

### 그런데 실제로는 이렇습니다

| 항목 | 사실 |
|---|---|
| **교환 횟수** | **양방향 2회.** A가 QR을 띄우면 B가 찍고, 이번엔 B가 QR을 띄워 A가 찍어야 연결된다. 두 기기가 서로의 화면을 물리적으로 볼 수 있어야 한다 |
| **같은 와이파이** | **서버가 진짜로 0.** 내부 IP만 쓰므로 STUN조차 필요 없다 |
| **서로 다른 망**(한쪽 LTE, 한쪽 집 와이파이) | **STUN 서버가 필요하다.** "내 공인 IP가 뭐냐"만 묻는 가벼운 무상태 서버지만 어쨌든 외부 의존이다. 그리고 양쪽 다 대칭형 NAT이면(약 10%) 중계 서버가 여전히 필요하다 |
| **원격 플레이** | **불가능.** 서로 화면을 못 보면 QR을 못 찍는다 |
| **연결이 끊기면** | **다시 찍어야 한다.** 화면 잠금·앱 전환으로 WebRTC가 죽는 것은 모바일에서 일상적이다 |
| **데이터 크기** | 일반 SDP는 2,500바이트가 넘어 QR 한 장에 안 들어간다. 전용 압축 프로토콜을 짜야 55~100바이트로 줄어든다 |
| **권한** | 카메라 권한 필요. iOS는 로컬 네트워크 권한도 별도로 묻는다 |

### 판정: 릴레이를 정본으로 유지한다. 이유는 두 가지입니다

1. **방 코드는 원격에서도 되고 QR은 안 된다.** 카카오톡으로 코드 한 줄(ABC-67)을 보내면 다른 도시에서도 붙는다. QR은 같은 방에 있어야만 성립한다.
2. **결정적인 것은 재연결이다.** 보드게임은 중간에 화면을 끄고 딴짓하는 일이 잦은데, QR 방식은 그때마다 두 사람이 다시 카메라를 들고 서로 화면을 찍어야 한다. 릴레이는 방 상태의 주인이 있어서 그냥 다시 들어오면 복구된다.

**다만 QR을 버리지는 않습니다.** 두 자리에 기록해 둡니다.

- **탈출구**: Cloudflare가 정책을 바꿔 릴레이가 죽으면 — 같은 방 플레이만이라도 **서버 없이 살릴 수 있는 유일한 경로**다. 계획의 위험 대응표에 넣는다.
- **선택 기능(2차 확장 이후)**: "같은 와이파이면 QR로 즉석 연결" 옵션. 통신 계층이 `Transport` 인터페이스 뒤에 격리돼 있으므로 게임 코드는 한 줄도 안 바뀐다.

## 3. 수록 게임

수요는 Board Game Arena(세계 최대 온라인 보드게임 사이트, 게임별 누적 대국 수 공개)의 실측치로 쟀다. **사목 458만 판·쿼리도 141만 판은 원본 페이지를 직접 열어 대조했고 정확히 일치했다.**

### T0 — 최소 출시 8종

| # | 게임 | 인원 | 모드 | 난이도 | 왜 이 순서인가 |
|---|---|---|---|---|---|
| 1 | **사목** (커넥트4 개명) | 2 | 공용·스플릿·멀티·AI | 1 | 연평균 74만 판 = **체스의 6배**, 조사 전체 1위. 7×6이 폰 세로에 최적 |
| 2 | **오목** (자유룰+스왑 오프닝) | 2 | 공용·멀티·AI | 2 | 교점 렌더러·위협 탐색 AI를 최초 생성 → 육목·바둑·고누가 물려받음 |
| 3 | **육목** | 2 | 공용·멀티·AI | 2 | 턴당 2수가 선수 이점을 상쇄해 금수 규칙이 아예 불필요 |
| 4 | **리버시** (오델로 개명) | 2 | 공용·멀티·AI | 2 | 흑백 돌이 UI 제약의 정통 표현. 체스로 이어질 AI 골격 확보 |
| 5 | **요트 다이스** | 1~4 | 전 모드 | 2 | 주사위 렌더러 + 점수표 = 점수판 축 전체의 모체 |
| 6 | **범용 점수판** | 제한없음 | 점수판·공용 | 2 | 점수판 시장 최대 단일 수요. 요트 점수표 파생이라 사실상 공짜 |
| 7 | **함대 격침** (배틀쉽 개명) | 2 | 공용·멀티·AI | 3 | **멀티 최초 도입 지점** — 턴당 좌표 1개라 통신 배관이 최소 |
| 8 | **체스** | 2 | 공용·멀티·AI | 2 | 판 전체를 한 줄(FEN 표기)로 보내 재접속·화면 불일치가 공짜로 해결 |

**순서 원칙은 "싼 게임 먼저"가 아니라 "싸면서 다음 것을 싸게 만드는 게임 먼저"다.**

확정 코어 중 **바둑만 미룬다** — 집 계산·사석 처리 상태기계가 바둑 공수의 절반이고 19×19는 폰 세로에서 성립하지 않는다. 규칙 한 줄짜리 **원자바둑**(먼저 한 점이라도 따내면 승)이 하루 비용으로 그 자리를 먼저 메운다.

### T1 — 1차 확장 (첫 자리는 벽길)

**벽길(쿼리도)** — 2~4인, 벽으로 상대 길을 막으며 반대편 끝에 먼저 도착하는 게임. 연평균 10.5만 판으로 체스(12.4만)와 사실상 동급인데 "추상전략 = 체스·바둑" 통념 밖에 있다. 벽이 굵은 검은 선이라 UI 궁합 최상. 이름은 Gigamic 상표이므로 개명.
최소 출시에 안 넣는 이유: **벽길만 새 알고리즘(벽마다 모든 말의 도달 경로를 너비 우선 탐색으로 검증)과 새 입력 방식(드래그 후 확정 2단계)을 동시에 요구한다.** 나머지 8종은 전부 격자에 돌 놓기라 서로 코드를 물려받는다.

나머지: 윷놀이 · 원자바둑 · 바둑(9×9) · 체커 · 도트앤박스 · 고누 · **숫자야구** · 사다리타기 · 다트 점수판 · 당구 점수판.

> **숫자야구가 T1의 숨은 요충지다.** 여기서 **커밋-리빌**(각자 답을 먼저 해시 지문으로 걸어 두고 나중에 공개해, 상대 답을 보고 자기 답을 바꾸지 못하게 하는 방식)을 처음 만든다. 이후 빙판·라이어 다이스·동시 커밋 게임이 전부 이것을 재사용한다.

### T2 — 2차 확장 게임풀

진입 조건: T0/T1에서 ① 멀티 실사용(방 생성 → 완주율)이 확인되고 ② 커밋-리빌이 검증되면.

**(가) 기존 엔진 재사용 — 거의 공짜**

| 게임 | 인원 | 모드 | 난이도 | 근거 |
|---|---|---|---|---|
| 안개 체스 | 2 | 멀티 | 2 | 체스 엔진 + 시야 함수 하나. chess.com 변형 수요 1위 |
| 함대 격침 변형(살보·이동함대) | 2 | 공용·멀티·AI | 1 | 렌더러 재사용 + 규칙 분기만 |
| 지뢰찾기 깃발 대전 | 2 | 공용·멀티·AI | 2 | 가림 없이 공용이 성립하는 유일한 은닉 게임 |
| 만칼라 | 2 | 공용·멀티·AI | 2 | 2×6 가로 배치 = 세로 폰 최적 |

**(나) 물리·동시 커밋 축 — 사용자 추가 요청분**

| 게임 | 인원 | 모드 | 난이도 | 판정 |
|---|---|---|---|---|
| **빙판** (동시 커밋 알까기) | 2~4 | 공용·멀티·AI | 3 | ★ **이 축의 정답.** 아래 상술 |

> **빙판** — 사용자 설계: 모두가 미리 *어느 방향·어느 세기*로 칠지 정하고, 턴이 끝나면 한꺼번에 움직인다. 진행에 따라 바닥이 사라진다.
>
> 조사 관점에서 이 설계는 **가장 다루기 쉬운 물리 게임**이다. 이유:
> 1. **입력이 이산적이다**(방향 + 세기 = 숫자 2개). 드래그 궤적 같은 연속값이 아니라 턴당 몇 바이트만 오간다.
> 2. **기기 간 물리 계산 일치가 필요 없다.** 권위 좌석이 한 번 계산하고 결과 좌표만 뿌린다(§1의 "판 전체 전송" 규칙이 그대로 적용).
> 3. **동시 커밋이 곧 커밋-리빌의 정확한 용처다.** 숫자야구에서 만든 것을 그대로 쓴다 — 남의 지시를 먼저 보고 자기 것을 바꾸는 부정이 원천 차단된다.
> 4. **3~4인이 자연스럽다.** 순번을 기다릴 필요가 없어 카탈로그의 약점(2인 편중)을 메운다.
> 5. 바닥이 사라지는 규칙은 **판을 강제로 끝내 준다** — 무승부·장기전이 없다.
>
> **알까기**는 원래 "물리 계산이 기기마다 달라 멀티 불가"로 T3 공용 한정이었으나, **권위 좌석이 계산하고 결과만 전송**하는 방식이면 그 문제가 성립하지 않는다(친 사람의 기기가 계산한다). T2 멀티로 올린다. 단 드래그 입력이 연속값이라 빙판보다 UI 손이 더 간다 → **빙판을 먼저, 알까기를 뒤에.**

## 4. 메인 화면과 로비 구조

**세부는 `docs/plan/room-lobby.md`에 있다.** 화면 흐름, 방 로비 레이아웃(방 코드·현재 게임 카드·
2×3 플레이어 격자·준비 상태), 방장 권한, 시작에 필요한 준비 인원, 방 코드 규격과 충돌 계산,
게임 목록 필터가 전부 그 문서에 있다. **여기에 복제하지 않는다** — 둘 중 하나가 반드시 낡는다.

전역 계획이 알아야 할 것만 남긴다:

- **흐름**: 이름(최초 1회) → 메인 3버튼(이 기기에서 플레이 · 방 참여 · 방 생성) → 방 로비 → 게임 목록.
  **이 기기에서 플레이는 로비를 건너뛰고 곧장 게임 목록으로 간다.**
- **방이 게임보다 먼저 존재한다.** 한 방에서 게임을 갈아 끼운다 — 오목 두다 요트로 넘어간다.
  매 판 방을 다시 만드는 기존 서비스 대비 실질 차별점이고 리듀서 레지스트리 설계와 맞는다.
- **"이 기기에서 플레이"는 화면 흐름만 건너뛸 뿐 코드 경로가 갈라지지 않는다.** 통신 계층
  (`Transport`)에 자기 자신에게 되돌려 주는 구현을 두어 혼자 하기·한 기기 공용·스플릿·여러 기기
  멀티가 전부 같은 경로를 탄다. 로비 코드가 두 벌로 갈라지는 것을 처음부터 막는다.
- **이름**은 최초 1회 입력하고 기기에 저장한다. 로그인이 아니라 표시용이고 서버에 남지 않는다.
- **방 코드는 `ABC-67`** — 영문 3자(`I`·`L`·`O` 제외 23자) + 숫자 2자, 대소문자 구분 없음.

## 5. 색 — 사용자 지정 4색 확정

**채택: `#FF0D22` 빨강 · `#21DB3B` 초록 · `#00AEFC` 파랑 · `#B500FC` 보라.**

노랑을 보라로 바꾼 것이 결정적으로 옳았다 — 순수 노랑은 흰 바탕 대비 **1.07:1**로 사실상 보이지 않아 원래 팔레트의 최대 결함이었다. 보라는 4.81:1로 4색 중 가장 진하다.

### 계산 결과

| | 흰 바탕 대비 | 적색맹이 보는 색 | 녹색맹이 보는 색 |
|---|---:|---|---|
| 1P `#FF0D22` | 3.94:1 | `#5F6027` 짙은 올리브 | `#949400` 올리브 |
| 2P `#21DB3B` | **1.86:1** | `#D0D03B` 밝은 노랑 | `#BCBD47` 연노랑 |
| 3P `#00AEFC` | 2.48:1 | `#A5A5FC` 연한 하늘 | `#9495FD` 연한 하늘 |
| 4P `#B500FC` | 4.81:1 | `#4040FC` 진한 파랑 | `#6767FA` 중간 파랑 |

**두 가지를 확인했습니다.**

1. **색약에서도 네 색이 구분된다** — 다만 (빨강·초록)과 (파랑·보라)가 각각 *같은 계열의 밝기 차이*로 좁혀진다. 그래서 **모양(●■▲◆)과 번호 병기는 선택이 아니라 필수**다. 색은 보조 신호다.
2. **초록의 흰 바탕 대비가 1.86:1로 낮다.** 그런데 이것은 **문제가 되지 않는다** — 접근성 기준(WCAG 1.4.11)은 *구성요소의 경계*에 적용되고, 이 계획은 모든 말·마커에 **검은 외곽선**을 두르기 때문에 경계 대비는 21:1이다. 채움색에 필요한 것은 흰 바탕 대비가 아니라 서로 간 구분이다.
   **단 하나의 금지 규칙**: 초록을 **가는 선이나 작은 글자에 단독으로 쓰지 않는다**(외곽선이 없는 요소). 채움 + 외곽선 조합에서만 쓴다.

### 파스텔 방향에 대해

"어둡게 말고 파스텔로"라는 방향은 맞지만, **파스텔과 흰 바탕은 직접 충돌합니다.** 파스텔 = 밝음 = 흰 바탕 대비 하락이고, 색약 구분도 같이 나빠집니다. 계산으로 확인했습니다:

| | 흰바탕 최저 대비 | 색약 최악 쌍 |
|---|---:|---:|
| 지정하신 4색 그대로 | 1.86 | 1.05 |
| 흰색 20% 섞음 | 1.70 | 1.04 |
| 흰색 35% 섞음 | 1.55 | 1.01 |

**지정하신 색이 이미 최적점입니다.** 제가 앞서 제안한 어두운 색보다 밝고 선명해서 "파스텔 계열"의 인상을 주면서도, 더 밝히면 손해만 납니다. 그대로 갑니다.

말·마커의 **채도는 색이 아니라 면적으로 조절**한다 — 큰 면적은 그대로 칠하고, 배경 하이라이트(내 차례 표시, 유효한 수 표시)에는 같은 색을 **투명도 12~15%**로 깐다. 이러면 화면 전체 인상은 파스텔이 되고 말 자체의 식별력은 유지된다.

### 다크 모드를 위해 지금 해 둘 것

다크 모드는 나중에 결정하기로 했지만, **지금 안 해 두면 나중에 못 하는 것**이 두 가지 있다.

**하나, 같은 4색을 어두운 배경에 그대로 쓰면 안 된다.** 계산해 보면 문제 되는 색이 뒤바뀐다:

| | 흰 바탕 | 짙은 회색 `#1A1A1A` | 순검정 |
|---|---:|---:|---:|
| 1P 빨강 | 3.94 | 4.42 | 5.33 |
| 2P 초록 | **1.86** ← 흰 바탕의 약점 | 9.33 | 11.26 |
| 3P 파랑 | 2.48 | 7.01 | 8.46 |
| 4P 보라 | 4.81 | **3.62** ← 어두운 배경의 약점 | 4.37 |

흰 바탕에서 가장 약한 건 초록인데, 검은 바탕에서 가장 약한 건 보라다. 그래서 "색을 조금 틀어야 한다"는 판단이 정확하다 — 다크 모드에서는 **보라를 밝게(`#D060FF` 방향), 초록을 조금 낮춰** 균형을 맞춘다. 구체값은 다크 모드를 실제로 켤 때 같은 방식으로 계산해 확정한다.

**둘, 그러려면 색이 한 곳에만 있어야 한다.** 색상값을 컴포넌트에 직접 쓰지 않고 **CSS 변수로만 참조한다**(`var(--p1)` 등). 이 규칙 하나면 나중에 다크 모드 팔레트 교체가 값 4~6개 수정으로 끝나고, 안 지키면 게임 20개를 뒤져야 한다. **돌의 음영 방향(§6)도 배경이 뒤집히면 반전돼야 하므로 같은 변수 체계에 묶는다.**

## 6. 화면 규칙

- **높이는 `100svh`** — 브라우저 주소창 상태와 무관한 최소 높이라 어느 순간에도 잘리지 않고, `dvh`와 달리 값이 실시간으로 변하지 않아 **손가락 아래 교차점이 움직이지 않는다**.
- **노치·홈 인디케이터**는 `viewport-fit=cover` + `env(safe-area-inset-*)`.
- **글꼴 크기**: `-webkit-text-size-adjust` 선언을 **넣지 않는다**. `<meta name="viewport" content="width=device-width">`가 있으면 크롬의 자동 글자 확대는 이미 발동하지 않으므로 불필요하고, 넣으면 OS 글꼴 크기 설정이 죽는다. 고정 높이를 금지하고, 실기기에서 **OS 글꼴 최대**로 놓고 점수판을 검수한다.
- 다크 모드를 제공하지 않더라도 `color-scheme: only light`는 **반드시 넣는다** — 안 넣으면 안드로이드 크롬의 자동 다크 모드가 페이지를 임의로 어둡게 칠한다.

### 돌 렌더링 사양 (확정 · 7종 공통)

**검은 외곽선 + 투톤 음영. 회색을 쓰지 않고 순백과 검정 두 색만으로 디더링해 음영을 만든다.**

- **광원은 좌상단.** 백돌은 **우하단 안쪽 가장자리를 따라 초승달 모양 음영**, 흑돌은 반대로 **좌상단에 초승달 하이라이트**.
- **음영 = 8:1 디더** — 3×3 픽셀 셀마다 반대색 1픽셀(검1 : 흰8, 약 11% 밀도). 이러면 팔레트가 문자 그대로 흑백 2색으로 유지된다.
- **외곽선 두께 = 지름의 약 11.5%.** 흑돌은 채움이 검정이라 외곽선이 보이지 않으므로 실질적으로 원 하나다.

**★ 크기 임계: 돌 지름 26px 미만이면 음영을 생략하고 순백 채움 + 외곽선만 쓴다.**

실제 렌더링으로 확인한 결과다. 22px 이하에서는 초승달 안에 들어가는 검은 픽셀이 두세 개뿐이라 **음영이 아니라 얼룩으로 보인다.** 반대로 34px 이상에서는 의도한 대로 하프톤 음영으로 읽힌다. 기기별 실측:

| 게임·기기 | 격자 간격 | 돌 지름 | 음영 |
|---|---:|---:|---|
| 사목 7×6 · 폰 390px | 55px | 50px | **켬** |
| 체스·리버시 8×8 · 폰 390px | 48px | 44px | **켬** |
| 바둑 9×9 · 폰 390px | 43px | 40px | **켬** |
| 바둑 19×19 · 태블릿 820px | 40px | 36px | **켬** |
| 오목 15×15 · 폰 390px | 24px | 22px | 끔 |
| 바둑 19×19 · 폰 390px | 19px | 17px | 끔 (애초에 태블릿 전용) |

음영이 꺼진 상태도 확인했는데 **오히려 더 깔끔하게 읽힌다** — 작은 화면에서 손해가 없으므로 이 임계는 타협이 아니라 정답이다.

**구현 함정 하나**: 디더는 픽셀 격자에 맞아야 하므로, **보드 셀 크기를 정수 CSS 픽셀로 스냅**한다(남는 몇 픽셀은 여백으로). 안 맞추면 확대·축소 시 무아레(물결 얼룩)가 생긴다. SVG에서는 `<pattern>`을 3px 셀로 정의하고 `shape-rendering="crispEdges"`를 건다.

## 6.5 AI 설계 — 단일 탐색 코어

### 결론: 됩니다. 하나의 코어가 카탈로그의 14종을 덮습니다

미니맥스 탐색기가 게임에 대해 알아야 하는 것은 네 가지뿐이고, **그중 둘은 이미 게임 엔진에 있습니다**:

| 필요한 것 | 상태 |
|---|---|
| `apply(상태, 수) → 상태` | **이미 있음** (리듀서 그 자체) |
| `terminal(상태) → 끝났나·누가 이겼나` | **이미 있음** (공통 계약 5개 중 하나) |
| `legalMoves(상태, 좌석) → 수 목록` | 게임이 추가로 제공 |
| `evaluate(상태) → 좌석별 점수` | 게임이 추가로 제공 |

즉 **게임당 추가 비용은 `legalMoves` + `evaluate` 두 함수(30~80줄)뿐**입니다. 나머지 탐색·가지치기·시간 관리·난이도 조절은 한 번만 만듭니다.

**코어가 덮는 게임(완전공개·확정적·순차 진행)**: 사목 · 오목 · 육목 · 리버시 · 체스 · 체커 · 벽길 · 고누 · 헥스 · 도트앤박스 · 만칼라 · 원자바둑 · 브레이크스루 · 다이아몬드 게임 → **14종**.

**코어 밖(각자 작은 전용 AI 또는 AI 없음)**: 요트(확률 → 기대값 계산 약 60줄) · 함대 격침(은닉 → 확률 밀도 탐색 약 40줄) · 라이어 다이스 · 카드류 · 빙판(동시 커밋) · 알까기(물리) · 파티·점수판(AI 없음).

이것이 §1의 엔진 설계와 정확히 맞물립니다 — `legalMoves`를 **필수가 아닌 선택 능력**으로 둔 이유가 여기서 회수됩니다. 요트·배틀쉽·점수판은 그 함수를 아예 안 가지면 되고, 가진 게임만 공짜로 AI를 얻습니다.

### 3~4인 게임에 봇을 앉히려면 (사용자 아이디어 ①)

평범한 미니맥스는 **2인 제로섬** 전용입니다. N명으로 넓히는 표준 방법이 둘 있고, 같은 뼈대에서 20줄 차이입니다:

- **max^n** — 각 좌석이 *자기* 점수를 최대화한다. 자연스럽지만 알파-베타 가지치기가 거의 안 먹혀 깊이가 얕아진다(3수 정도).
- **paranoid** — "나머지 전원이 나를 노린다"고 가정한다. 가지치기가 그대로 먹혀 더 깊이 보고, 실전에서 대체로 더 잘 둔다.

**권고: max^n을 기본, paranoid를 옵션으로.** 3~4인 게임(벽길 4인·만칼라·다이아몬드)은 깊은 전술 게임이 아니라 3수면 충분합니다. **"3명이서 4인 전용 게임" 요구는 이걸로 성립합니다.**

**"AI 상대로 살아남기"(사용자 아이디어 ②)** 는 paranoid 모델을 그대로 뒤집은 것 — 한 좌석이 나머지 전원을 상대합니다. 추가 코드가 사실상 없습니다.

### 강도 — "중수와 호각, 고수는 확실히 이김"

5수 앞이 맞는 목표치입니다. 다만 **5수만 넣으면 멍청해 보이는 게 아니라 고장 나 보입니다.** 값싼 보강 세 가지가 그 경계를 가릅니다:

1. **정지 탐색(quiescence)** — 말을 주고받는 도중에 계산을 멈추지 않고 교환이 끝날 때까지 더 본다. **이게 없으면 체스·체커 AI가 5수 지평선 바로 너머에서 말을 공짜로 헌납한다.** 약 30줄. 사용자가 말한 "게임 자체가 성립이 안 되는 느낌"의 대부분이 이 한 가지에서 나온다.
2. **위협 연장(오목·육목)** — 연속 게임의 위협은 5수보다 멀리 뻗는다. 위협이 걸린 가지만 더 깊이 판다. 두 게임이 공유.
3. **반복 심화 + 시간 예산** — 고정 깊이가 아니라 "X밀리초까지 판다". 낡은 폰에서 화면이 멈추지 않고, **난이도 조절 손잡이가 공짜로 생긴다.**

예상 강도: 사목·리버시·오목·육목은 5수 + 위 보강으로 중수급(리버시는 **종반 마지막 10수 완전탐색 약 20줄**을 꼭 넣는다 — 없으면 끝에 어이없이 진다). 체스는 정지 탐색 있는 5수가 대략 1400~1500 수준으로, **동네 강자와 호각이고 고수에게는 확실히 집니다.** 스펙과 일치합니다.

**난이도를 낮추는 방법**: 깊이를 줄이고(5→3→2) 최선수 대신 상위 몇 개 중에서 고릅니다. **무작위 수를 섞지 않습니다** — 무작위는 "봐준다"가 아니라 "고장났다"로 읽히고, 그게 정확히 피하려는 것입니다.

### 부피 예산

| 항목 | 예산 | 횟수 |
|---|---:|---|
| 탐색 코어 (알파-베타 + max^n + 정지 탐색 + 반복 심화 + 전치표 + 시간 예산) | **250줄** | 1회 |
| 게임당 `legalMoves` + `evaluate` | 30~80줄 | 해당 게임만 |
| 코어 밖 전용 AI (요트·함대 격침) | 40~60줄 | **필요한 것만** |

**AI는 이 프로젝트의 주역이 아닙니다.** 코어 250줄을 한 번 쓰고 나면 게임 추가 비용이 두 함수로 떨어지므로, 그 이상 부풀리지 않습니다. 코어는 **M1(오목·육목·리버시)에서 만듭니다** — 그때 세 게임이 동시에 쓰므로 추상화가 실물로 검증됩니다. M0의 사목 AI는 코어 없이 직접 짜고(사목은 5수 탐색이 30줄), **M1에서 코어로 흡수하면서 첫 사용자가 됩니다.**

### 배포 파이프라인

1. GitHub에 push
2. **Cloudflare Pages가 직접 빌드**해서 배포 (Git 연동). **GitHub Actions YAML을 쓰지 않는다** — 워크플로 파일은 액션 폐기·Node 상향으로 1~2년 안에 조용히 썩는다
3. GitHub Pages 미러는 `dist/`를 `git subtree push` 한 줄로 (역시 Actions 없음)
4. 릴레이 Worker는 **별도 배포**(`wrangler deploy`). 정적 자산 요청은 Worker 한도(10만 요청/일)와 **섞이지 않으므로**, 릴레이 배포 실수가 사이트를 죽이지 못한다
5. **화면 구석에 빌드 해시를 상시 표시** — 이게 없으면 배포 연동이 끊긴 걸 몇 달간 모른다

### 주소(도메인)

브라우저 저장은 **주소 단위**라, 나중에 주소를 바꾸면 **사용자의 저장된 판과 점수 기록이 전부 사라진다.** 도메인 구매(연 1~2만 원)는 취향이 아니라 데이터 보존 정책의 일부다.

**결정: 지금은 사지 않고 `*.pages.dev`로 시작한다**(§9-5). 그 대가와 완화책은 §9의 주석 참조 — 요약하면 JSON 내보내기/가져오기가 완화책이고 이미 필수 기능이라 추가 비용이 없으며, **옮길 거면 사용자가 적을 때 옮기는 게 싸다.**

|---|---|---|
| 1 | 저장소·빌드·배포 골격 | Vite + Preact + TS, 정확 버전 고정, 리셋 CSS 직접 작성, `dist/` 커밋, Cloudflare Pages 연동, GitHub Pages 미러 |

| 3 | SVG 보드 렌더러 + 말 렌더링 | `viewBox` 단일 스케일, **정수 셀 스냅**, 원판 = 검은 외곽선 + 채움 + 모양(●■▲◆) + 번호. 사목은 플레이어 4색을 쓰므로 **흑백 돌의 8:1 디더 음영은 M0 범위가 아니다** — M1(오목·리버시)에서 같은 렌더러에 얹는다 |
| 4 | 로비 + `Transport` 인터페이스 | 이름 입력 → 방(만들기 / 코드 입장 / 이 기기에서 플레이) → 게임 목록(인원 구분·태그·검색). **loopback 구현으로 로컬이 멀티와 같은 코드 경로** |

| 6 | PWA | 서비스워커 약 80줄(HTML network-first), manifest, **빌드 해시 상시 표시**, 업데이트 배너(무조건 즉시 적용 금지) |
| 7 | 사목 AI | 5수 탐색, Web Worker(`worker.format='iife'`), 타임아웃 + 탐욕 폴백. **탐색 코어 추상화는 만들지 않는다** — M1에서 3게임이 동시에 쓸 때 도출한다 |

**완료 조건 — 실기기 검수 7** ✅ **2026-08-12 7/7 전부 통과** (사용자 실기기 확인). 기계 검증 4항도 통과. **M0 완료.** (사용자만 가능): ① 공용 대국 완주 ② AI 대국 완주 ③ 다른 기기와 방 코드로 붙어 완주 ④ 비행기 모드 실행 ⑤ 배포 후 빌드 해시 변경 확인 ⑥ OS 글꼴 최대에서 레이아웃 정상 ⑦ **"이 기기에서 플레이"가 멀티와 같은 코드 경로로 동작**

## 12. 이름 (확정 2026-08-12)

**서비스명 `Nollawa`. 인게임 타이틀만 `Nollawa party games`.**
