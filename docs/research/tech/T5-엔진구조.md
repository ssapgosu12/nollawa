# T5 — 엔진 구조 / 상태 동기화 (조사·판정)

조사일: 2026-08-12 · 웹검색 수행함(하단 출처)
전제: 무료·P2P만 · 1년 방치 생존 최우선 · 유지보수 인력 0 · 구현은 Codex 위임

---

## 0. 한 줄 결론

**"턴제 보드게임 공통 엔진"을 만들려 하지 마라. 공통층은 게임이 아니라 `리듀서 + 액션 로그 + 스냅샷 전송 + 로컬 저장` 네 가지뿐이고, 이건 400~600줄이다. 그 위는 게임 가족(family)별로 갈라라.**
동기화는 **호스트 권위 + 매 수마다 상태 전체 스냅샷 브로드캐스트**. 무브 로그 재현(lockstep)은 이 프로젝트에서 순손해다.

---

## 1. 공통 추상화 — 어디까지 공유하고 어디서 갈라지는가

### 1.1 실패하는 방식(전형적 함정)

```ts
// ❌ 이렇게 하면 죽는다
interface Game<S, M> {
  init(): S
  legalMoves(s: S, player: number): M[]
  applyMove(s: S, m: M): S
  winner(s: S): number | null
  evaluate(s: S): number
  isDraw(s: S): boolean
  undo(s: S): S
  // ... 15개쯤 되면 절반이 NotImplemented를 던진다
}
```

이 인터페이스에 다음이 안 들어간다:

| 게임 | 안 맞는 이유 |
|---|---|
| 요트 다이스 | 한 턴이 `굴림 → 킵 선택 → 재굴림 → 킵 → 재굴림 → 카테고리 선택`. "수(move)"가 단일 개념이 아니고 중간에 난수가 낀다. `legalMoves`가 32개 킵마스크 + 13개 카테고리라는 이종(異種) 집합이 된다. |
| 배틀쉽 | 배치 페이즈는 **동시**(둘이 같이 놓는다), 사격 페이즈는 교대. 그리고 상태의 절반이 상대에게 보이면 안 된다. `legalMoves`는 "안 쏴본 칸"이라 자명한데 정작 필요한 건 비공개 분리다. |
| 파티 게임 | 동시 입력 + 타이머. 턴이라는 개념이 없다. |
| 점수판 | **게임이 아니다.** 합법 수도 승패도 없다. |
| 육목(Connect6) | 한 턴에 돌 2개. `M`이 단일 좌표가 아님. |

`GateState`를 유니온으로 만들어 `dice?`, `hiddenBoard?`, `timer?`, `phase?`를 옵셔널로 계속 붙이는 것이 이 함정의 말기 증상이다(신(神)상태, god state). 20개 게임에서 옵셔널 필드가 40개 붙고, 어느 필드가 어느 게임에서 유효한지 아무도 모르게 된다.

### 1.2 채택안 — 3계층

#### Tier 0 · 진짜 공통 (20개 게임 + 점수판 전부)

```ts
// core/contract.ts  — 전체 40줄 남짓. 이게 공통층의 전부다.
export type Seat = 0 | 1 | 2 | 3

export interface Ctx {
  /** 호스트만 호출. 게스트 리듀서는 이걸 절대 부르지 않는다(§3) */
  random: () => number
  now: number          // 호스트가 찍어 넣는다. Date.now()를 리듀서 안에서 부르지 마라
}

export interface Module<S, A> {
  id: string
  version: number                       // 저장 마이그레이션용
  init(cfg: Config, ctx: Ctx): S
  reduce(s: S, a: A, ctx: Ctx): S       // 순수함수. 입력 변형 금지
  seatsToAct(s: S): Seat[]              // 빈 배열 = 종료 또는 대기
  terminal(s: S): Result | null
  redact?(s: S, viewer: Seat): S        // 기본 = identity (§4)
  migrate?(old: unknown, fromVersion: number): S
}
```

이게 왜 이걸로 충분한가: **직렬화는 계약에 넣을 필요가 없다.** 상태를 "JSON으로 왕복 가능한 값만" 쓰기로 규칙을 정하면 `serialize/deserialize`는 `JSON.stringify/parse`이고 계약에서 사라진다. 계약에서 메서드 2개를 지우는 대신 **린트 규칙 하나**(상태에 `Map`/`Set`/클래스 인스턴스 금지)를 얻는 게 훨씬 싸다.

`legalMoves`는 **Tier 0에 없다.** 이게 이 설계의 핵심 판정이다. 합법 수 생성은 (a) AI가 쓰고 (b) UI가 놓을 수 있는 칸을 하이라이트할 때 쓰는데, 두 용도 다 게임별 코드에서 직접 부르면 된다. 공통 계약에 넣는 순간 요트·파티·점수판이 더미 구현을 갖게 된다.

#### Tier 1 · 선택적 능력(capability) — 필요한 게임만 구현

```ts
// 게임 모듈이 "추가로" 만족할 수 있는 인터페이스. 상속이 아니라 덕타이핑.
export interface Enumerable<S, A> { legalMoves(s: S, seat: Seat): A[] }
export interface Scored<S>        { evaluate(s: S, seat: Seat): number }
export interface Clocked<S>       { tick(s: S, dtMs: number): S }
```

`Enumerable`을 만족하면 → 범용 AI 하네스(§5)와 "놓을 수 있는 칸 표시" UI를 공짜로 붙일 수 있다. 만족 안 하면 그냥 안 붙는다. 런타임 체크는 `'legalMoves' in mod` 한 줄.

#### Tier 2 · 가족(family)별로 갈라진다 — 여기서는 공유하지 마라

```
families/
  grid-stones/     오목 · 육목            ← 같은 파일 하나, 파라미터로 분기
  grid-classic/    체스 · 바둑            ← 렌더러(격자+좌표)만 공유, 규칙은 완전 분리
  dice/            요트                   ← phase 상태머신
  hidden-grid/     배틀쉽                 ← redact 사용
  party/           파티 게임 N종          ← 로그 없이 로컬 ephemeral 상태 허용
  tally/           점수판                 ← 게임 레지스트리에 등록하지 않는다
```

**오목/육목은 두 게임이 아니라 파라미터 하나다.** `{ boardSize: 15|19, stonesPerTurn: 1|2, winLength: 5|6, firstTurnStones: 1 }`. 승패 판정·수 생성·렌더링 100% 공유. 이건 진짜 공유고, 공짜다.

**체스와 바둑은 공유하지 마라.** 둘 다 "격자에 두는 게임"이라는 표면 유사성이 있지만, 체스는 피스 이동·특수 규칙(캐슬링·앙파상·프로모션)·체크 판정이고 바둑은 활로·따냄·패(ko)·집 계산이다. 공유 가능한 건 **격자를 그리는 React/Svelte 컴포넌트 하나**뿐이며, 그건 UI 계층이지 엔진이 아니다.

**점수판은 게임 레지스트리에 넣지 마라.** 단, `reduce` + 액션 로그는 쓴다 — 점수판이야말로 **되돌리기(undo)가 가장 절실한 화면**이기 때문이다(실물 게임 중 점수 오입력은 1순위 사고). Tier 0의 로그를 쓰면 undo/redo가 공짜다. 메뉴·라우팅상으로는 게임과 별도 섹션.

### 1.3 판정 요약

| 계층 | 무엇 | 예상 규모 |
|---|---|---|
| Tier 0 코어 | contract · 액션 로그 · undo · 저장/복원 · 마이그레이션 | 250~350줄 |
| 전송 | 호스트 권위 프로토콜 · 좌석 · 재접속 | 250~350줄 |
| AI 하네스 | 워커 RPC · 취소 · 타임아웃 | 100~150줄 |
| **공통층 합계** | | **600~850줄** |
| 게임 1개 | 오목/육목(둘 합쳐) 300 · 요트 400 · 배틀쉽 350 · 체스 900~1400 · 바둑 700~1100 · 파티 1종 80~150 · 점수판 250 | |

**"공통층이 800줄을 넘어가면 추상화가 게임을 삼키고 있다는 신호"** — 이걸 예산으로 문서에 못 박아 두면 Codex가 계약을 부풀리는 걸 막을 수 있다.

## 2. 동기화 모델 — 전체 상태 vs 무브 로그

### 2.1 크기 계산 (판정의 근거)

| 게임 | 상태 실측 추정 | JSON 바이트 |
|---|---|---|
| 오목 15×15 | 225칸 Int8 | ~500 B (배열 JSON) |
| 육목 19×19 | 361칸 | ~800 B |
| 바둑 19×19 | 361칸 + 따냄수 + 패 위치 + **초superko용 과거 국면 Zobrist 해시 400개** | ~1.2 KB (해시를 8B hex로) |
| 체스 | FEN 70 B + 기보 | ~1.5 KB |
| 배틀쉽 | 10×10 ×2 사격판 + 함대 2×5척 | ~600 B |
| 요트 | 주사위 5 + 점수표 13×N + phase | ~400 B |

**최악이 ~1.5 KB.** 한 수 간격은 보드게임에서 5~30초. 즉 대역폭은 **초당 50~300바이트**. WebRTC DataChannel의 실용 상한(브라우저 간 상호운용 안전선 16 KB/메시지)에 한참 못 미친다.

→ **전체 상태 전송의 비용은 0이다.** 그러면 남는 건 "무브 로그 방식이 대가로 무엇을 요구하는가"뿐이다.

### 2.2 무브 로그(lockstep)가 요구하는 것 — 그리고 왜 이 프로젝트를 죽이는가

무브만 보내고 각자 재현하려면 **양쪽 리듀서가 비트 단위로 같은 결과**를 내야 한다. 필요 조건:

1. `Math.random`·`Date.now` 리듀서 안에서 금지 (통제 가능)
2. 부동소수점이 상태에 못 들어감 (통제 가능)
3. 객체 키 순회 순서 의존 금지 (통제 어렵다 — 숫자형 키 객체는 삽입 순서가 아니라 오름차순으로 순회된다)
4. **★ 양쪽이 같은 앱 빌드를 돌려야 한다** ← 이게 치명타

4번이 결정적이다. 이 앱은 PWA다. 서비스 워커가 A의 기기에는 구버전을, B의 기기에는 신버전을 캐시해 둔 상태가 **정상적으로 발생한다**(SW 업데이트는 다음 방문에나 반영되고, 사용자는 앱을 며칠씩 안 닫는다). 무브 로그 방식에서 이 상황은 **조용한 디싱크**로 나타난다 — 에러 없이 두 사람의 화면이 다른 판이 되고, 며칠 뒤 "가끔 게임이 이상해져요"라는 재현 불가능한 버그로 돌아온다. 유지보수 인력 0인 프로젝트에서 이건 사형선고다.

전체 상태 방식에서 같은 버전 스큐는 **우아하게 열화**한다: 신버전이 추가한 필드를 구버전이 무시할 뿐, 판은 갈라지지 않는다.

### 2.3 채택안 — 호스트 권위 + 스냅샷

```ts
// 게스트 → 호스트 : "의도(intent)"만 보낸다. 상태를 직접 바꾸지 않는다.
type ToHost =
  | { t: 'join';   clientId: string; sessionId: string; name: string }
  | { t: 'intent'; action: unknown }
  | { t: 'ping' }

// 호스트 → 게스트 : 매번 상태 전체(수신자별 redact 적용)
type ToGuest =
  | { t: 'seat';  seat: Seat, gameId: string }
  | { t: 'sync';  seq: number; state: unknown; last?: unknown }  // last = 애니메이션 힌트
  | { t: 'error'; code: 'illegal' | 'not-your-turn' | 'full' }
```

호스트 루프 (실질 50줄):

```ts
function onIntent(from: Seat, action: A) {
  if (!mod.seatsToAct(state).includes(from)) return send(from, {t:'error', code:'not-your-turn'})
  let next: S
  try { next = mod.reduce(state, action, ctx) } catch { return send(from, {t:'error', code:'illegal'}) }
  if (next === state) return                       // 무변화 = 불법수로 간주
  state = next; seq++
  for (const p of peers) send(p, { t:'sync', seq, state: view(state, p.seat), last: action })
  persist()                                        // §5
}
```

게스트는 `sync`를 받으면 **자기 상태를 통째로 교체한다.** 병합 없음, 롤백 없음, 예측 조정 없음. 낙관적 미리보기(내가 놓은 돌을 즉시 반투명으로 표시)는 순수 UI 상태로 두고 다음 `sync`에서 버린다.

**전체 상태를 고른 것의 세 번째 배당금**: 게스트 전원이 완전한 복제본을 들고 있으므로,
- 재접속 = 호스트가 현재 스냅샷 1개 보내면 끝 (§5)
- 호스트 이탈 시 승계 = `seq`가 가장 큰 게스트가 호스트가 되면 끝 (~40줄)

이 둘은 무브 로그 방식에서는 각각 "로그 전체 재전송 + 재현"과 "로그 권위 이전 + 분기 해소"가 되어 몇 배로 복잡해진다.

### 2.4 기각한 대안

- **JSON Patch / 델타 동기화**: 1.5 KB를 아끼려고 패치 생성·적용·순서 보장 코드를 200줄 추가한다. 절약액이 0에 수렴하므로 순손해.
- **CRDT (Yjs / Automerge)**: 동시 편집 충돌 해소가 핵심 가치인데, **턴제 게임에는 동시 편집이 없다**(한 번에 한 명만 둔다). 게다가 "규칙에 맞지 않는 상태로 병합되는 것"을 CRDT는 막지 못한다 — 보드게임에서 필요한 건 병합이 아니라 **거부**다. 의존성 크기도 크다.

## 3. 결정론 · 주사위 · 셔플

### 3.1 시드 공유는 필요 없다

호스트 권위 + 스냅샷을 고른 순간, **게스트는 난수를 재현할 필요가 없다.** 호스트가 굴리고 결과를 상태에 담아 보낸다. 공유 시드 PRNG는 코드에서 **삭제** 대상이다.

시드가 여전히 필요한 곳은 딱 두 군데:
- **테스트**(§6 리플레이 테스트) — 주입 가능한 `ctx.random`으로 해결
- 훗날 "이 판 다시보기" 기능 — 로그에 굴림 결과가 이미 들어 있으므로 시드 불필요

→ `ctx.random`은 **호스트에서 `crypto.getRandomValues` 래핑, 테스트에서 시드 PRNG 주입**. 인터페이스 하나, 구현 둘. 20줄.

### 3.2 호스트가 주사위를 조작할 수 있는 문제 — 판정

세 가지를 실제로 따져 봤다.

**(a) commit-reveal**: 각자 `H(nonce)` 커밋 → 공개 → XOR로 시드. Web Crypto `crypto.subtle.digest('SHA-256')`은 보안 컨텍스트(HTTPS)에서 항상 쓸 수 있으므로 PWA에선 무조건 가용. **코드는 40줄인데 문제는 실패 경로다** — 커밋과 공개 사이에 상대가 끊기면 타임아웃·롤백·재시도가 필요하고, 요트에서 한 게임에 굴림이 39회(13턴 × 3)이므로 그 실패 경로를 39번 통과한다. 버그가 사는 곳이 정확히 여기다.

**(b) 게임 시작 nonce 혼합 + `H(seed ‖ rollIndex)`**: 굴림당 왕복 없음, 25줄. 그런데 **치명적 결함이 있다 — seed가 전원에게 알려지므로 누구나 다음 5번의 굴림을 미리 계산할 수 있다.** 요트에서 미래 주사위를 아는 건 호스트 조작보다 훨씬 강력한 부정행위다. **기각.**

**(c) 아무것도 안 함 (호스트가 `crypto.getRandomValues`로 굴림)**: 아무도 예측할 수 없다. 호스트만 편향 가능하되, **편향하려면 앱을 수정해 빌드해야 한다**(devtools로 내부 함수를 부르는 수준으로는 이미 굴려서 로그에 박힌 값을 못 바꾼다 — §3.3).

**판정: (c). commit-reveal은 이 프로젝트에 과하다.**
결정적 근거는 암호학이 아니라 **헌장이다**: 랜덤 매칭 없음 · 랭킹 없음 · 로그인 없음. **부정행위로 얻을 것이 존재하지 않는다.** 이기려고 앱을 리빌드하는 친구를 막는 코드를 쓰는 대신, 그 친구와 게임을 안 하면 된다.

### 3.3 대신 넣을 것 (거의 공짜)

- 모든 굴림·셔플 결과를 **액션 로그에 남기고** "기록 보기" 화면에서 노출 (30줄). 사회적 해법: 의심되면 로그를 보여 달라고 하면 된다.
- 굴림은 **하나의 액션으로 원자적으로** 처리한다: `{t:'roll'}` 인텐트 → 호스트가 결과를 확정해 `seq`를 올리고 즉시 브로드캐스트. 호스트가 "굴려 보고 마음에 안 들면 리로드"를 하면 브로드캐스트된 `seq`가 이미 나가 있으므로 게스트가 stale 상태를 거부한다. 이 한 줄(`if (msg.seq <= mySeq) return`)이 **가장 흔한 캐주얼 부정행위(리로드 리롤)를 실제로 막는다.**

## 4. 비공개 정보

### 4.1 문제

전체 상태를 보내면 게스트가 devtools의 네트워크/메모리에서 상대 함대를 볼 수 있다.

### 4.2 채택안 — `redact(state, viewer)` 하나로 통일

```ts
// battleship/index.ts
redact(s, viewer) {
  return {
    ...s,
    fleets: s.fleets.map((f, i) => i === viewer ? f : null)   // 상대 함대 = null
  }
}
```

전송층은 수신자마다 `mod.redact?.(state, seat) ?? state`를 직렬화해 보낸다(§2.3의 `view()`). 게임당 5~15줄, 전송층 플러밍 10줄.

이걸로 **게스트는 상대 배치를 절대 받지 못한다.** 남는 구멍: **호스트는 자기 메모리에 양쪽 함대를 다 들고 있다.**

### 4.3 그 구멍을 막을 것인가 — 판정

막는 방법은 "각자 자기 함대를 자기 기기에만 두고, 상대는 `fire(x,y)`를 보내고 소유자가 `hit/miss/sunk`로 답한다"(실물 게임과 동일)이다. 40줄이면 되고 호스트조차 못 본다.

**그런데 이건 두 번째 권위 모델을 코드베이스에 도입한다.** 게임 20개 · 유지보수 0인 프로젝트에서 "이 게임은 호스트 권위, 저 게임은 좌석 분산 권위"는 재접속·호스트 승계·저장 복원 경로를 각각 두 벌 만들게 한다.

**판정: `redact`만 채택하고, 호스트가 볼 수 있다는 사실은 감수한다.**
근거: **하나의 권위 모델을 지키는 값어치가, 친구 사이의 부정행위 하나를 막는 값어치보다 크다.** 암호학적 해법(셀별 해시 커밋, 머클 트리)은 **명백히 과잉**이며, 어차피 클라이언트가 "맞았다/빗나갔다"를 정직하게 공개한다는 신뢰가 전제되므로 근본 해결도 못 된다.

### 4.4 보완 (싸고 효과적)

- **종료 후 검증**: 게임이 끝나면 양쪽이 함대를 공개하고, 클라이언트가 사격 로그와 대조해 모순(맞았어야 할 칸을 miss로 답함)을 자동 검출 (30줄). **예방이 아니라 탐지** — 이게 친구 게임에 맞는 해법이다.
- **비공개 상태도 반드시 로컬 저장한다.** 함대가 자기 기기에만 있는 부분이 있다면 배치 확정 즉시 IndexedDB에 쓴다. 안 그러면 새로고침 한 번에 게임이 복구 불능이 된다.
- 규칙: **비공개 필드는 이름에 접두사 `_secret`을 붙인다.** 그러면 §6의 자동 유출 테스트가 게임별 지식 없이 전부를 검사할 수 있다.

## 5. 재접속 · 중단 복구

두 개의 다른 문제다. 섞지 마라.

### 5.1 로컬 복구 (앱이 죽었다 / 탭을 닫았다 / 배터리가 나갔다)

```ts
// 저장 단위: 게임당 1개 슬롯 + "진행 중" 인덱스
type Save = {
  gameId: string; version: number
  state: unknown; log: unknown[]; seq: number
  room?: { code: string; role: 'host'|'guest'; seat: Seat }
  savedAt: number
}
```

- 저장소: **IndexedDB**. `localStorage`가 아니다 — 동기 API라 큰 상태에서 프레임을 먹고, iOS Safari의 ITP는 **7일 미사용 시 localStorage를 삭제**한다. 설치된 PWA + `navigator.storage.persist()`를 요청하면 훨씬 안전하다.
- 저장 시점: 액션마다 300ms 디바운스 + **`visibilitychange`가 `hidden`이 될 때 즉시 flush**.
  **`beforeunload`/`unload`를 쓰지 마라** — 모바일 브라우저(특히 iOS)에서 상당수 발화하지 않는다. `pagehide`/`visibilitychange`가 신뢰할 수 있는 유일한 훅이다.
- 상태가 1.5 KB 이하이므로 **상태와 로그를 둘 다 저장**한다. 로그는 undo용.
- 버전 마이그레이션: `version` 불일치 시 `mod.migrate`가 있으면 호출, 없으면 **저장을 버리고 "이전 판을 불러올 수 없습니다"를 보여 준다.** 1년 방치 프로젝트에서 마이그레이션 체인을 유지하는 것은 부채다 — 게임당 마이그레이션은 만들지 말고 폐기를 기본값으로 두되, 점수판만은 예외로 마이그레이션을 쓴다(실물 게임 기록은 버리면 안 되는 데이터다).

### 5.2 피어 재접속 (네트워크가 끊겼다 / WiFi↔LTE 전환)

**WebRTC PeerConnection은 네트워크 전환에서 살아남지 못한다.** ICE restart로 살릴 수 있지만 PeerJS/trystero 레벨에서 깔끔하게 노출되지 않는다.

**채택: 모든 재접속을 "같은 방 코드로 새로 입장"으로 처리한다.** 전체 상태 스냅샷을 골랐기 때문에 재동기화는 `sync` 메시지 1개다.

좌석 유지:

```ts
const clientId  = ls('clientId')  ?? crypto.randomUUID()   // localStorage, 영속
const sessionId = crypto.randomUUID()                       // 탭마다 새로

// 호스트: clientId → seat 매핑을 들고 있다가 재입장 시 같은 좌석 반환.
// 같은 clientId가 다른 sessionId로 오면 이전 세션을 축출(두 탭 열기 대응).
```

- **유예 시간**: 피어 소실 후 60초는 "재접속 대기" 상태로 두고 타이머를 멈춘다. 그 뒤에 이탈로 처리.
- **호스트가 나간 경우**: 자동 승계는 만들지 마라(스플릿 브레인 버그 공장). 게스트 화면에 "호스트 대기 중… [내가 호스트 되기]" 버튼을 띄우고 **수동 승계**(~40줄). `seq`가 가장 큰 사람이 누르면 된다.
- **NAT 현실**: 2026년 기준 소비자 WebRTC 세션의 **약 15~20%가 직접 P2P에 실패해 TURN 릴레이가 필요**하고, 이동통신망은 대부분 CGNAT(대칭 NAT)라 STUN 홀펀칭이 실패한다. 엔진 관점의 함의는 하나다: **"연결 실패"는 예외가 아니라 정상 경로다.** 연결 실패 시 방 코드를 유지한 채 재시도 UI로 떨어지도록 상태 기계를 짜라(연결 상태를 게임 상태에 섞지 말 것 — 별도 스토어).

## 6. 쉬운 AI — 정직한 규모 추정

수치는 **실측이 아니라 엔지니어링 추정**임을 명시한다.

### 6.1 오목 (15×15)

| 구성요소 | 줄 수 | 비고 |
|---|---|---|
| 패턴 평가기 (4방향 라인 스캔, open-3/closed-4/open-4/five 테이블) | 150~250 | 여기가 실질 전부 |
| 후보 수 제한 (기존 돌 반경 2칸) → 분기 225 → **30~50** | 20 | 이게 없으면 어떤 최적화도 무의미 |
| 알파-베타 + 반복심화 + 수 정렬 | 150~200 | |
| 즉승/즉방어 사전 검사 | 30 | **체감 강도의 절반이 여기서 나온다** |
| **합계** | **~400~500** | |

성능: 정렬된 알파-베타 깊이 4는 수만 노드, 노드당 평가가 4방향×9칸. TypedArray 기반이면 **수~수십 ms**. 깊이 6이 **수백 ms** 수준. 1초 예산 반복심화면 워커에서 여유롭다.

### 6.2 육목 (Connect6, 19×19)

**정직하게: 여기서 미니맥스를 시도하지 마라.** 한 턴에 돌 2개 → 분기 계수가 `C(후보,2)`로 폭발한다(후보 60개면 1,770). 깊이 2조차 300만 노드.

현실적 설계: 위협 기반 그리디 + 1.5수 읽기.
1. 단일 착점 후보를 평가해 상위 20개 추림
2. 그 안에서 쌍 조합 상위 ~50개만 생성
3. 각 쌍에 대해 상대의 **최선 응수 쌍 1개**만 계산해 감점
→ 200~250줄 추가. **"강하지 않지만 창피하지 않은" 수준.** 이걸 문서에 명시해 기대치를 고정해야 Codex가 무한히 튜닝하는 걸 막는다.

### 6.3 배틀쉽 — **투자 대비 효과 1위**

확률 밀도(probability density) 탐색:
- 안 침몰한 함선마다 가능한 모든 배치를 격자에 슬라이딩, 기존 miss/sunk와 충돌하면 스킵, 통과하면 해당 칸 히트맵 +1
- 미해결 hit이 있으면 hunt 모드(그 hit을 덮는 배치만 카운트)
- **패리티**: 가장 짧은 함선 길이 L에 대해 `(x+y) % L === 0`인 칸만 우선 탐색 — **5줄로 성능이 눈에 띄게 오른다**

연산량: 함선 5척 × 배치 ~120 = 600 배치 × 평균 4칸 ≈ **2,400 연산/수**. 마이크로초 단위. **워커 불필요.**
줄 수: **120~180줄.** 이 정도로 거의 최적에 가깝게 둔다. 배틀쉽 AI는 반드시 만들어라.

### 6.4 요트 다이스

**전체 최적 솔버(약 10^8 상태 DP)는 절대 하지 마라.**

현실적: **1단계 전방탐색**
- 현재 굴림에서 킵 부분집합 32개(2^5) 전부 열거
- 각각에 대해 재굴림 결과 분포를 계산 — 주사위 5개의 **다중집합(multiset)은 252개뿐**이므로 확률 테이블을 앱 시작 시 1회 프리컴퓨트
- `E[남은 카테고리 중 최선 점수]`를 정적 카테고리 가치 함수로 계산
- 연산량: 32 × 252 ≈ **8,000회** → 1ms 미만. **워커 불필요.**

줄 수: **250~350줄.** 이 중 카테고리 채점 테이블(~100줄)은 게임 자체에 어차피 필요하므로 AI 순증분은 ~200줄.
(2단계 전방탐색은 32×252×32×252 ≈ 6,500만 → JS에서 0.3~1초. 하고 싶다면 워커 + 메모이제이션. **권장하지 않음** — 1단계로 이미 사람보다 잘 둔다.)

### 6.5 체스 / 바둑

**헌장대로 만들지 않는다.** 다만 요청이 나올 것에 대비한 사실:
- 체스: `stockfish.wasm`을 얹는 방법이 있으나 **멀티스레드 빌드는 COOP/COEP 응답 헤더가 필요하고, GitHub Pages는 응답 헤더를 설정할 수 없다.** 반드시 **단일 스레드 빌드**를 쓸 것(1~7 MB 에셋). Netlify/Cloudflare Pages는 `_headers`로 가능.
- 바둑: 약한 바둑 AI는 없느니만 못하다. **하지 마라.**

### 6.6 워커 플러밍

```ts
// ai/host.ts — 메인 스레드 쪽. Comlink 안 씀.
const w = new Worker(new URL('./ai.worker.ts', import.meta.url), { type: 'module' })
const pending = new Map<number, (v:any)=>void>()
w.onmessage = e => { pending.get(e.data.id)?.(e.data.result); pending.delete(e.data.id) }

export function think(gameId: string, state: unknown, budgetMs = 1000, timeoutMs = 3000) {
  const id = ++n
  return Promise.race([
    new Promise(res => (pending.set(id, res), w.postMessage({ id, gameId, state, budgetMs }))),
    delay(timeoutMs).then(() => (w.postMessage({ id, abort: true }), fallbackGreedy(gameId, state)))
  ])
}
```

- **Comlink 채택하지 않음.** 1.1 kB에 API는 훌륭하지만, 60줄을 아끼자고 GoogleChromeLabs 의존성(릴리스 주기 느림)을 추가하는 건 "1년 방치" 기준에서 감점이다. 게다가 프록시 해제(`releaseProxy`) 누락 시 워커 참조가 새는 실제 함정이 있다.
- **타임아웃과 그리디 폴백은 필수다** — iOS Safari는 백그라운드 탭의 워커를 종료시켜서 응답이 영원히 안 온다.
- 워커 1개에 `switch (gameId)` 디스패치. 게임마다 워커 파일 만들지 마라(번들 증가 + PWA 캐시 목록 관리 부담).
- 취소: 반복심화의 각 ply 사이에서 abort 플래그를 확인한다(워커는 메시지를 처리 중엔 못 받으므로 `SharedArrayBuffer` 없이는 즉시 중단 불가 — ply 경계 확인이 현실적 타협).

## 7. 테스트 전략 — 회귀만 잡는 최소 집합

원칙: **UI가 바뀌어도 안 깨지고, 동작이 진짜 바뀔 때만 깨지는 테스트.** E2E(Playwright)는 브라우저 바이너리를 받아야 하고 1년이면 확실히 깨진다 → **채택하지 않음.**

### 7.1 규칙 오라클 테스트 (가치 1위)

**체스 = perft.** 이게 이 프로젝트 전체에서 투자 대비 효과가 가장 높은 테스트다.

```ts
// 알려진 정답표 — 표준값
test.each([
  ['startpos', 1, 20], ['startpos', 2, 400], ['startpos', 3, 8902],
  ['startpos', 4, 197281], ['startpos', 5, 4865609],
  ['kiwipete', 3, 97862],   // 캐슬링·앙파상·핀이 얽힌 표준 함정 포지션
])('perft %s depth %i', (fen, d, expected) => expect(perft(fen, d)).toBe(expected))
```

테스트 코드 **30줄**로 체스 수 생성 1,000줄 이상을 전수 검증한다. 캐슬링 통과 칸 체크, 앙파상, 프로모션, 핀 — 버그가 하나라도 있으면 숫자가 어긋난다. JS에서 perft(5)는 수 초.

- **바둑**: 따냄 / 자살수 / 패(ko) / 초超패(superko) 각각 고정 국면 표 + 9×9 종국 3판의 집 계산.
- **오목·육목**: **경계 승패 판정** — 4방향 × 모서리/변에서의 off-by-one이 실제 최다 버그. 20케이스.

### 7.2 리플레이 테스트 (범용 회귀 알람)

```ts
// fixtures/gomoku-001.json  =  { gameId, seed, actions: [...], finalHash: "…" }
for (const f of loadFixtures()) {
  test(f.name, () => {
    const ctx = { random: seeded(f.seed), now: 0 }
    let s = mod(f.gameId).init(f.cfg, ctx)
    for (const a of f.actions) s = mod(f.gameId).reduce(s, a, ctx)
    expect(sha256(JSON.stringify(s))).toBe(f.finalHash)
  })
}
```

하네스 **20줄**로 20개 게임 전부를 덮는다. 픽스처는 한 번 플레이해서 자동 기록.
**함정: 이건 변경 탐지기(change detector)라 정당한 규칙 수정 때 반드시 갱신해야 한다.** `npm run fixtures:update` 한 명령으로 재생성되게 만들지 않으면 6개월 안에 전부 skip 처리되어 썩는다.

### 7.3 레지스트리 전수 불변식 테스트 (게임별 지식 0)

등록된 모든 게임에 자동 적용되는 4개. **새 게임을 추가하면 자동으로 검사된다** — 이게 20개 규모에서 결정적이다.

```ts
for (const m of ALL_MODULES) describe(m.id, () => {
  test('JSON 왕복', () => expect(JSON.parse(JSON.stringify(s))).toEqual(s))
  test('리듀서 불변', () => { deepFreeze(s); expect(() => m.reduce(s, a, ctx)).not.toThrow() })
  test('금지 타입 없음', () => expect(hasMapSetClassOrUndefined(s)).toBe(false))
  test('redact 유출 없음', () => {
    const s2 = plantSecrets(s)                      // 비공개 필드에 magic token 심기
    expect(JSON.stringify(m.redact!(s2, 0))).not.toContain('__SECRET__')
  })
})
```

`deepFreeze` + `reduce`가 안 던지는지 확인하는 테스트는 **호스트/게스트 상태 분기의 1위 원인(상태 변형)** 을 잡는다. 총 30~50줄.

### 7.4 2-인스턴스 전송 시뮬레이션

호스트와 게스트를 같은 프로세스 안의 평범한 객체로 만들고 메시지를 배열로 주고받되, "드롭/재정렬/지연"을 주입할 수 있게 한다. 네트워크 없이 가장 무서운 코드를 테스트한다.

- 메시지 5개 드롭 후 재입장 → 게스트 상태가 호스트와 일치하는가
- stale `seq` 거부되는가
- 같은 `clientId` 재입장 시 같은 좌석을 되찾는가
- 호스트 수동 승계 후 `seq`가 이어지는가

**~80줄. 반드시 만들어라.**

### 7.5 AI 위생 테스트

- 오목: 즉승 있으면 둔다 / 상대 열린4 있으면 막는다 (10케이스)
- 배틀쉽: 밀도 선택 칸이 기존 miss와 모순되지 않는다
- 요트: 야추가 이미 나왔으면 5개 다 킵한다

### 7.6 도구와 "1년 방치" 방어

- 러너: **Vitest 4.x** (2026년 활발히 유지보수 중, Vite와 무설정 통합). 대안 `node:test`는 의존성 0이라 더 방치-내성이 있지만 TS 처리에 결국 도구가 붙는다 → Vitest로 충분.
- **★ 가장 큰 방치 방어 레버는 코드가 아니라 정책이다**: `package.json`에서 **캐럿(`^`) 제거하고 정확한 버전 핀 + lockfile 커밋 + `npm ci`**. 1년 뒤 빌드가 깨지는 최다 원인은 내 코드가 아니라 의존성 트리 표류다.
- 의존성 총량 목표: **런타임 의존성 2개 이하**(P2P 라이브러리 1개 + UI 프레임워크 1개), 개발 의존성 3개 이하(Vite, Vitest, TypeScript).
- CI: 공개 레포면 GitHub Actions 무료. 15줄짜리 `npm ci && npm test`면 충분.
- 총 테스트 케이스 **60~120개, 전부 순수 함수, 10초 이내**.
