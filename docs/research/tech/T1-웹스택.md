## 0. 한 줄 결론

**Vite + TypeScript + Preact 10 (TSX), 메타프레임워크·상태관리·CSS프레임워크 없음. 모든 보드는 SVG.
게임 규칙 엔진은 프레임워크 import가 0인 순수 TS 모듈로 분리. boardgame.io는 기각. Phaser/PixiJS는 기각.**

핵심 논리: **배포된 정적 산출물은 썩지 않는다. 썩는 것은 "다시 빌드할 수 있는 능력"이다.**
따라서 최적화 대상은 런타임이 아니라 **직접 의존성 개수와 빌드 설정 표면적**이다.

## 1. 용어 (이 문서 안에서만 통하는 축약 금지 원칙)

- **VDOM(Virtual DOM, 가상 DOM)** — 화면을 자바스크립트 객체로 한 번 만들고 이전 것과 비교해 바뀐 부분만 실제 화면에 반영하는 방식. React·Preact가 쓴다.
- **런타임 크기** — 사용자가 첫 화면을 보기 위해 반드시 내려받아야 하는 프레임워크 자체의 용량. 게임 코드는 별도.
- **코드 스플리팅** — 앱 전체를 한 덩어리로 내려받지 않고, 지금 필요한 조각만 나눠 내려받는 것.
- **트리셰이킹** — 빌드할 때 실제로 안 쓰는 코드를 잘라내는 것.
- **SSR(Server Side Rendering, 서버 사이드 렌더링)** — 서버가 HTML을 미리 만들어 보내는 것. **이 프로젝트는 서버가 없으므로 전혀 필요 없다.**
- **PWA(Progressive Web App)** — 브라우저로 접속하지만 홈 화면에 설치되고 오프라인에서도 뜨는 웹앱.
- **서비스워커** — PWA가 오프라인으로 돌게 해 주는, 브라우저에 상주하며 네트워크 요청을 가로채는 스크립트.
- **`viewBox`** — SVG에서 "이 그림의 좌표계는 가로 380, 세로 380이다"라고 선언하는 속성. 화면 픽셀과 무관한 자체 좌표계를 만든다.
- **dvh/svh** — 모바일 브라우저 주소창이 나타났다 사라지는 것까지 반영한 화면 높이 단위(`100vh`의 후속).
- **Rolldown** — Vite 8부터 들어간 Rust로 다시 짠 번들러. 기존 Rollup을 대체했다.

## 3. boardgame.io — **명시적 기각**

프로젝트와 목적이 겹치므로 가장 먼저 결론을 낸다.

### 3.1 유지보수 상태: GitHub는 살아 있지만 **npm은 4년째 죽어 있다**

- 마지막 npm 배포: **`0.50.2` / 2022-11-10.** 조사 시점 기준 **3년 9개월**.
- GitHub `main`에는 2026년 7~8월 커밋이 있다. 그러나 내용은 Dependabot 자동 PR과 툴링 현대화
  (최근 커밋 예: "Migrate ESLint to flat config so ESLint 9 can land (#1325)").
  **코드는 움직이는데 릴리스가 안 나온다** = `npm install boardgame.io` 하면 2022년 코드를 받는다.
- 이슈 #1150의 제목이 "Whats the state of the project?"라는 것 자체가 상태를 말해 준다.
  이슈 51개·PR 8개가 열린 채 누적.

**"1년 방치해도 돌아가야 한다"는 이 프로젝트의 최상위 목표를, 라이브러리 자신이 이미 위반하고 있다.**

### 3.2 의존성 트리가 프로젝트 제약과 정면 충돌

`boardgame.io@0.50.2`의 dependencies (실측):

```
koa ^2.13.3, koa-body ^5.0.0, @koa/cors ^3.1.0, @koa/router ^10.1.1, koa-socket-2 ^2.0.0,
socket.io ^4.5.0, socket.io-client ^4.1.3, redux ^4.1.0, immer ^9.0.5, nanoid ^3.1.30,
svelte ^3.41.0, svelte-json-tree-auto ^0.1.0, flatted ^3.2.1, p-queue ^6.6.2,
rfc6902 ^5.0.0, prop-types ^15.5.10, react-cookies ^0.1.0, setimmediate ^1.0.5,
ts-toolbelt ^6.3.6, lodash.isplainobject ^4.0.6, @types/koa, @types/koa__router
```

- **Koa + socket.io = 상시 가동 서버 프레임워크**를 클라이언트 설치에 끌고 들어온다.
  프로젝트 제약은 "무료 호스팅 또는 P2P만, 상시 가동 서버 = 프로젝트를 죽이는 요인"이다.
  번들러가 트리셰이킹으로 최종 번들에서는 뺄 수 있어도, **`node_modules` 설치 표면·`npm audit` 표면·
  공급망 공격 표면은 그대로 남는다.**
- `svelte ^3` — 이미 두 세대 지난 버전을 강제로 끌고 온다. 우리가 Svelte 5를 쓰든 안 쓰든 설치된다.
- `immer ^9`, `redux ^4` — 모두 그 사이 메이저가 올라갔고 보안 패치 흐름에서 떨어져 있다.
- 직접 의존성만 **22개**. 우리 목표는 **3개 이하**다.

### 3.3 P2P 전용 모드가 실제로 되는가 — **된다고 볼 수 없다**

- P2P 트랜스포트는 본체가 아니라 별도 패키지 `@boardgame.io/p2p`다.
  **마지막 배포 0.4.4 / 2022-11-28.** peerDependency는 `boardgame.io >= 0.49.1`.
- 그 의존성: `peerjs ^1.3.2` + `tweetnacl`. PeerJS 자체도 마지막 배포가 **2025-06**로 활발하지 않다.
- 결정적으로 PeerJS는 **시그널링 서버(방 코드로 두 기기를 만나게 해 주는 중개 서버)가 필요**하다.
  기본값은 PeerJS 팀이 무료로 돌리는 공용 서버(`0.peerjs.com`)인데, SLA도 보증도 없는 제3자 인프라다.
  → "1년 방치해도 돌아가야 한다"에 정면 위배. 프로젝트가 죽는 방식이 **우리 코드가 아니라 남의 무료 서버**가 된다.
- 즉 boardgame.io P2P 경로를 택하면, **4년 묵은 라이브러리 + 4년 묵은 어댑터 + 남의 무료 시그널링 서버**의
  3중 의존이 된다.

### 3.4 얻는 것 대비 잃는 것

boardgame.io가 실제로 주는 것: 턴 순서 관리, 불변 상태(immer), 무르기(undo/redo), 로그, 결정론적 난수, 관전자 뷰.
우리가 만들 게임은 체스·바둑·오목·육목·배틀쉽·요트 + 파티게임 + 점수판이고, **어차피 게임별 규칙 엔진 20개를 직접 짜야 한다.**
그 위에 얹히는 턴 관리 골격은 게임당 순수 TS **150~250줄** 수준이다.

**판정: 기각. 단, 설계는 차용한다.**
`{ G(게임상태), ctx(턴 문맥), moves(순수 함수) }` 형태의 리듀서 패턴과 시드 고정 난수는
boardgame.io의 좋은 아이디어이므로 **의존성 없이 우리 코드로 재현**한다. 이렇게 하면
스냅샷 저장(localStorage), 무르기, P2P 전송(무브 객체만 주고받기), 리플레이가 전부 공짜로 따라온다.

## 4. 렌더링 방식 판정 — DOM/CSS vs Canvas vs SVG

### 4.1 실제 요소 개수부터 센다 (추측 금지)

| 보드 | 격자 | 최대 노드 수 |
|---|---|---|
| 바둑 19x19 | 선 38개 → **`<path>` 1개**, 화점 9, 돌 ≤361 | **약 375** |
| 오목 15x15 | `<path>` 1, 돌 ≤225 | 약 230 |
| 육목(연륙목) 19x19 | 바둑과 동일 | 약 375 |
| 체스 8x8 | 칸 64(또는 `<pattern>` 1), 기물 ≤32 | 약 100 |
| 배틀쉽 10x10 x2 | 칸 200, 마커 ≤200 | 약 400 |
| 요트 다이스 | 보드 아님(주사위 5 + 점수표) | 50 미만 |

**최대 약 400 노드.** SVG의 실용적 성능 한계는 통상 **3,000~5,000 노드**에서 시작한다고 알려져 있다.
즉 **우리는 SVG 한계의 10분의 1도 안 쓴다.** Canvas로 갈 성능적 이유가 존재하지 않는다.

### 4.2 SVG 채택 근거 (5가지, 이 프로젝트 조건에 한정)

**(1) 선명도 — "흰 바탕 + 검은 선"은 문자 그대로 벡터 선화다.**
SVG 선은 어떤 확대율·어떤 화면 밀도(레티나/저가 안드로이드)에서도 코드 한 줄 없이 머리카락처럼 선명하다.
Canvas는 `devicePixelRatio`(화면 픽셀 밀도)를 직접 곱해 주고, 화면 크기·회전·브라우저 확대가 바뀔 때마다
전부 다시 그려야 한다. 게다가 사용자가 **손가락으로 핀치 확대**하면 Canvas는 이미 그려진 래스터를
확대하므로 **뿌옇게 번진다.** SVG는 확대해도 다시 계산된다.
→ 이 프로젝트의 UI 규격(흰 바탕·검은 선)에서 SVG는 단순히 유리한 정도가 아니라 **정확히 맞는 도구**다.

**(2) 확대·폰트 스케일 — 프로젝트의 명시된 필수 요구사항.**
`viewBox="0 0 380 380"` + `width:100%`만 있으면 보드는 **미디어쿼리 0개로** 폰·태블릿·PC에 맞춰진다.
Codex가 픽셀 계산을 할 일이 없어지므로 "작은 세로 화면에서 잘림"의 최대 원인이 구조적으로 제거된다.
Canvas는 OS 텍스트 확대 설정에 완전히 불투명하다 — 시스템 글씨 크게 설정을 해도 캔버스 안 글자는 그대로다.
접근성 관점에서 막다른 길이다.

**(3) 터치 히트박스 — 19x19 바둑판의 실제 문제.**
360px 폭 스마트폰에서 19열 = 셀 약 **18px**. WCAG 최소 터치 타깃 24px, Apple 권장 44px에 한참 못 미친다.
SVG에서는 **보이는 격자와 별개로 투명한 `<rect>` 히트 타깃**을
(`fill="transparent"` + `pointer-events="all"`) 시각 셀보다 크게, 서로 겹치게 깔 수 있다.
Canvas였다면 좌표 → 교차점 역산 + 최근접 탐색 + 경계 처리를 손으로 짜야 한다(= Codex 버그 표면 증가).

**(4) 접근성 — 공짜로 얻는다.**
SVG 노드는 DOM 노드이므로 `role="button"`, `aria-label="D4"`, `tabindex`를 그대로 붙일 수 있다.
키보드 조작과 스크린리더가 추가 작업 없이 동작한다. Canvas는 그린 내용을 접근성 트리에 **아무것도** 노출하지 않는다.

**(5) 구현 난이도 — Codex가 보드 좌표로 사고하게 만든다.**
SVG는 정수 보드 좌표(0~18)를 그대로 쓴다. 픽셀 변환이 코드에서 사라지므로
LLM이 가장 자주 틀리는 부류(경계 오프셋, 반올림, DPI 배율)가 통째로 없어진다.

### 4.3 DOM/CSS Grid를 안 쓰는 이유

체스·배틀쉽처럼 **말이 칸 안에 있는** 게임은 CSS Grid가 아주 잘 맞는다.
그러나 바둑·오목·육목은 **돌이 칸이 아니라 선의 교차점 위에** 놓인다.
CSS Grid로 이걸 하려면 가장자리 반칸 처리, 격자선을 셀 배경으로 흉내내기, 화점 오버레이가 필요하고
전부 억지스러워진다.

**결정적 이유는 성능이 아니라 일관성이다.** 렌더링 모델을 두 개(체스=DIV, 바둑=SVG) 쓰면
Codex가 관리해야 할 패턴이 2배가 되고, 게임이 20개로 늘 때 그 혼선이 그대로 누적된다.
→ **보드는 전부 SVG 하나로 통일.** 체스에서 CSS Grid가 조금 더 편한 것은 그 대가로 지불한다.

### 4.4 DOM/CSS가 맡을 영역

메뉴, 게임 선택 화면, 점수판 표, 요트 다이스 점수표, 설정, 방 코드 입력, 토스트.
**여기서는 SVG를 쓰지 말 것** — 텍스트 줄바꿈·표 레이아웃·스크롤은 HTML/CSS가 압도적으로 우월하고,
OS 폰트 크기 설정도 여기서만 정상 반영된다.

### 4.5 Canvas를 쓰는 조건 (사실상 없음)

- 노드가 3,000개를 넘거나
- 파티클/연출 애니메이션이 60fps로 상시 도는 경우

두 조건 모두 이 프로젝트에 해당하지 않는다("애니메이션이 거의 없고 정적인 격자·말·숫자").
**예외 후보 1개**: 파티 게임 중 자유 드로잉(그림 맞히기류)이 들어간다면 그 게임 **하나만** Canvas.
그때도 보드 게임 쪽은 건드리지 않는다.

### 4.6 게임별 최종 렌더링 배정

| 게임 | 렌더링 | 비고 |
|---|---|---|
| 바둑 19x19 | SVG | 격자 = `<path>` 1개, 돌 = key 기반 `<circle>` |
| 오목 15x15 | SVG | 바둑과 동일 컴포넌트 재사용 |
| 육목 19x19 | SVG | 동일 |
| 체스 8x8 | SVG | 기물 = 인라인 `<symbol>` + `<use>` (폰트·이미지 의존 0) |
| 배틀쉽 10x10 | SVG | 두 보드 나란히, 배치 드래그는 pointer 이벤트 |
| 요트 다이스 | HTML/CSS + 주사위만 SVG | 점수표는 `<table>` |
| 점수판 (실물게임용) | HTML/CSS | 표 + 큰 숫자, SVG 불필요 |
| 파티 게임 | HTML/CSS (드로잉만 예외적 Canvas) | |

### 4.7 SVG를 쓸 때 반드시 지킬 것

```
격자선   : <path d="M10 10H370M10 30H370..."/>  ← 선 38개를 <line> 38개로 만들지 말 것
확대 대응: 격자 <path>에 vector-effect="non-scaling-stroke"
돌 갱신  : 매 수마다 361개 전부 재생성 금지. key 기반으로 바뀐 노드만.
터치     : 보드 컨테이너에 touch-action: manipulation
좌표     : viewBox 정수 좌표만 사용. 픽셀 계산을 코드에 남기지 말 것.
```

## 5. 프레임워크 후보 판정

### 5.1 메이저 업그레이드 강제 전력 (프롬프트가 요구한 근거)

| 스택 | 강제 마이그레이션 이력 | 다음 강제 이주 예고 |
|---|---|---|
| **Preact** | 10.x가 **2019-10부터 약 7년 무중단**. 그 사이 메이저 강제 없음 | 11은 2025-09부터 **아직 베타**, 안정판 일정 미발표. 10.x는 계속 패치(10.29.8 / 2026-08-01) |
| React | 16→17 이벤트 위임 루트 변경 / 18 StrictMode 이중 실행·자동 배칭 / 19 forwardRef 무력화·propTypes 제거·컴파일러 도입 | 약 2년 주기 반복 |
| Svelte | 3→4 툴링 · **4→5는 반응성 모델 자체 교체(runes)** | 5.x 안정. 다만 4→5 상흔이 LLM 학습 데이터에 그대로 남음 |
| SvelteKit | 1→2를 약 1년 만에 | 어댑터·라우팅 규약이 변화 진원지 |
| Vue | 2→3 대규모 이주(악명), Vue 2는 2023-12 EOL | 3.x는 안정적 |
| Solid | 1.x 안정 | **2.0 베타(2026-05)** — async/Suspense/배칭 전면 개편. **이주가 앞에 놓여 있다** |
| Vite | 5→6→7→8을 약 2.5년에 / **8은 번들러 엔진 교체(Rolldown)** | 빌드를 하는 한 회피 불가 |
| Phaser | **3→4 렌더러 전면 교체(2026-04)** | WebGL 전용 기능 확대 |

**읽는 법**: 우리는 유지보수 인력이 사실상 0이다. "이주가 쉬운가"가 아니라
**"이주를 요구받지 않는가"**가 기준이다. 이 기준에서 Preact 10이 압도적 1위다.

### 5.2 런타임 크기 / 콜드 스타트

압축(brotli) 후 대략치:

| 스택 | 런타임 | 첫 화면 목표 도달성 |
|---|---|---|
| 없음(바닐라) | 0 KB | 최상 |
| **Preact 10** | **약 4~5 KB** | 3G에서도 여유 |
| Solid 1.x | 약 7 KB | 좋음 |
| Svelte 5 | 런타임 약 10~15 KB + **컴포넌트별 컴파일 산출물이 개수에 비례해 증가** | 게임 20개 규모에서 고정 런타임보다 커질 수 있음 |
| Vue 3 | 약 35 KB | 보통 |
| React 19 | 약 45 KB | 무거움 |
| PixiJS 8 | 약 350 KB+ | 실격 |
| Phaser 4 | 약 800 KB~1.2 MB | 실격 |

**Svelte에 대한 흔한 오해 교정**: "Svelte는 런타임이 없다"는 Svelte 3 시절 이야기다.
Svelte 5는 런타임이 있고, 게다가 **컴포넌트 수에 비례해 컴파일 코드가 늘어난다.**
게임 20개 × 화면 3~4개 규모에서는 "고정 4KB VDOM 런타임 + 얇은 컴포넌트"가 총량에서 이길 가능성이 높다.
(이건 측정 대상으로 남긴다 — 아래 §8 미검증 가정 참조.)

**목표 수치**: 첫 화면(게임 선택 메뉴) 압축 후 **30KB 이하**, LTE 1초 이내, 3G 3초 이내.
Phaser/Pixi는 이 목표를 한 자릿수 배율로 초과하므로 **논의 없이 실격**.

### 5.3 게임 20개 코드 스플리팅 전략

```
src/
  main.ts                    ← 부팅 + 라우팅(해시 기반 30줄, 라우터 라이브러리 없음)
  registry.ts                ← 게임 메타데이터만 (id, 이름, 인원, 아이콘, 로더 함수)
  ui/                        ← 공통: SVG 보드 골격, 턴 표시, 버튼, 점수 저장소
  games/
    go/       { rules.ts(순수 TS), view.tsx, ai.ts }
    gomoku/   ...
    chess/    ...
```

- `registry.ts`에는 **메타데이터와 `() => import('./games/go')` 로더만** 둔다.
  메뉴 화면은 게임 코드를 **1바이트도 로드하지 않고** 20개 목록을 그린다.
- Vite는 동적 `import()` 지점마다 자동으로 청크를 쪼갠다. 별도 설정 불필요.
- 게임 카드에 `pointerenter`/`touchstart`가 발생하면 `<link rel="modulepreload">`로 선로딩 →
  탭했을 때 이미 받아져 있다.
- 이 구조의 핵심 이득: **게임이 6개에서 20개로 늘어도 첫 화면 크기가 상수로 유지된다.**
- 규칙 엔진(`rules.ts`)은 프레임워크 import가 0이므로, 나중에 UI 프레임워크를 갈아엎어도
  **가장 값비싼 자산(게임 로직 + AI)은 그대로 살아남는다.** 이것이 프레임워크 선택 리스크의 진짜 헤지다.

### 5.4 Codex(LLM)가 실수를 덜 하는 순서

1. **Preact/React TSX** — 학습 데이터 밀도가 압도적으로 높다. Preact는 React API의 부분집합이면서
   **그 부분집합이 7년째 안 움직였다.** 즉 오래된 학습 데이터가 오히려 정답이다. 이 조합은 드물다.
2. **바닐라 TS + DOM** — 프레임워크 지식이 필요 없다. 단, 게임 20개에 걸쳐 손으로 DOM을 동기화하면
   상태-화면 불일치, 리스너 누수 같은 버그를 Codex가 반드시 만든다. 이게 바닐라를 1위로 못 놓는 이유다.
3. **Vue 3** — Options API와 Composition API 두 문법이 공존해 모델이 섞어 쓴다.
4. **Svelte 5** — **확인된 문제.** 대부분의 모델이 Svelte 4 문법(`export let`, `$:`)에 압도적으로
   학습되어 있어 runes 프로젝트에 4 문법을 쓴다. 호환 모드 때문에 **컴파일은 통과하고 반응성만 조용히 죽는다.**
   Svelte MCP 서버·전용 스킬 같은 보정 도구가 별도로 존재한다는 사실 자체가 이 문제의 크기를 증명한다.
   **리뷰 인력이 0인 프로젝트에서 "조용히 잘못 동작"은 최악의 실패 유형이다.**
5. **Solid** — `props`를 구조분해하면 반응성이 소리 없이 끊긴다. React 습관으로 모델이 상습적으로 저지른다.

### 5.5 SvelteKit / Next 류 메타프레임워크 — 기각

우리는 **서버가 없고, SSR이 필요 없고, 라우트가 20개짜리 평면 목록**이다.
메타프레임워크가 제공하는 파일 기반 라우팅·로더·어댑터·서버 액션은 전부 쓰지 않는다.
쓰지 않는 기능의 **버전 변화만 고스란히 떠안는다**(SvelteKit은 1→2를 1년 만에 했고, 어댑터가 그 진원지).
해시 라우터 30줄로 충분하다.

## 6. 1년 방치 내구성 — 구조적 대책

### 6.1 무엇이 실제로 썩는가

- **배포된 정적 파일은 썩지 않는다.** HTML/JS/CSS/SVG가 CDN에 얹혀 있으면 1년이든 3년이든 그대로 뜬다.
- **썩는 것은 재빌드 능력이다.** 1년 뒤 `npm install`을 하는 순간 깨진다:
  - Vite 8(2026-03)은 `build.rollupOptions` → **`build.rolldownOptions`로 개명**했고,
    **ESM 전용**이 되었으며, **Node 20.19+ / 22.12+**를 요구한다.
  - TypeScript 7(Go 포팅판)이 나와 있다.
  - 전이 의존성 중 하나가 보안 권고로 강제 승격될 수 있다.

### 6.2 대책 (전부 적용)

1. **직접 의존성 3개 이하**: `vite`, `typescript`, `preact`. 끝.
   상태관리·라우터·CSS프레임워크·유틸 라이브러리 전부 금지.
2. **`package-lock.json` 커밋 + 정확 버전 고정**(캐럿 `^` 금지). 재현 가능한 빌드가 최우선.
3. **`dist/` 빌드 산출물을 저장소에 커밋**(또는 `gh-pages` 브랜치에 고정).
   → 빌드 도구가 깨져도 **사이트는 계속 살아 있다.** 이게 가장 값싼 보험이다.
4. **`vite.config.ts`를 15줄 이하로 유지.** 설정 옵션이 적을수록 개명·폐기에 맞을 확률이 낮다.
5. **게임 규칙 엔진에 프레임워크 import 금지.** `rules.ts`는 순수 TS 입력→출력 함수.
   프레임워크가 죽어도 로직은 산다. 테스트도 브라우저 없이 돈다.
6. **CSS는 손으로.** Tailwind 같은 도구는 v3→v4에서 설정 방식 자체가 바뀌었다(설정 파일 → CSS 지시자).
   흰 바탕·검은 선·4색 플레이어 구분이 전부인 UI에 CSS 프레임워크는 순수한 부채다.
   CSS 변수 10개 정도면 충분하다.

### 6.3 npm 생태계 붕괴 위험 (2026년 실사)

이건 이론적 우려가 아니다:

- **Shai-Hulud 웜** (2025-09 최초, 2025-11 V2): npm 패키지를 자가 전파로 감염시켜 빌드 환경의
  자격증명을 탈취하고 그 자격증명으로 계속 퍼졌다. **사람 조작 없이.**
  V2는 `postinstall`이 아니라 **`preinstall` 훅**을 써서 **설치가 실패해도 페이로드가 실행**되게 만들었다.
- 누적 피해: **1,300개 이상의 패키지 버전**, 합산 월 20억 다운로드 규모.
  `keyv`, `cacheable`, `flat-cache`, `file-entry-cache` 같은 흔한 유틸이 포함됐다.
- 2026-08에는 **ChainDrop**이라는 자가 전파 웜이 별도로 보고됐다(Microsoft Security).

**함의**: 모든 전이 의존성은 잠재적 침해 경로다. 의존성 개수 최소화는 취향이 아니라 **보안 요구사항**이다.
그리고 이것이 **boardgame.io의 22개 런타임 의존성이 결격 사유인 두 번째 이유**다.

**운용 규칙**: 가능한 한 `npm ci --ignore-scripts`. CI에서 `npm audit --omit=dev` 확인.
새 의존성 추가는 "이거 없으면 못 만드나?"를 통과해야만.

## 8. 다른 축과 충돌 가능 지점 · 미검증 가정

### 충돌 가능
- **P2P 축(T-멀티)**: boardgame.io 기각으로 **방 코드 P2P를 직접 구현해야 하는 부담이 그 축으로 넘어간다.**
  후보는 PeerJS(시그널링 서버 필요) 또는 Trystero 0.25.3(2026-07 활발, 공용 릴레이 이용).
  단 Trystero도 **제3자 공개 릴레이 인프라에 의존**하므로 "1년 방치" 기준에서는 별도 검증이 필요하다.
  T1은 이 판정을 하지 않는다.
- **호스팅 축**: SSR·서버 함수를 전혀 쓰지 않으므로 **순수 정적 호스팅이면 무엇이든 된다.**
  만약 다른 축이 메타프레임워크(SvelteKit/Next)를 전제로 호스팅을 골랐다면 그 전제는 무효다.
- **AI 상대 축**: 규칙 엔진을 프레임워크 무관 순수 TS로 두라는 T1의 요구는,
  AI를 Web Worker로 돌리려는 설계와 잘 맞는다(오히려 유리). 충돌 없음.
- **접근성/디자인 축**: SVG 강제는 디자인 자유도를 약간 제약한다(그림자·필터가 CSS만큼 편하지 않음).
  흰 바탕·검은 선 규격에서는 문제되지 않지만, 나중에 화려한 테마를 원하면 마찰이 생긴다.

### 미검증 가정 (반증되면 재판정)
1. **저가 안드로이드에서 361노드 SVG의 착수 반응 속도를 실측하지 않았다.**
   "3,000~5,000 노드가 한계"는 일반 자료 기반이고 우리는 약 400이라 여유롭지만,
   진짜 변수는 노드 수가 아니라 **매 수마다 얼마나 다시 그리는가**다. 프로토타입에서 측정 필요.
2. **Svelte 5의 "컴포넌트 수에 비례한 코드 증가 vs Preact 고정 런타임" 교차점을 측정하지 않았다.**
   게임 20개 규모에서의 총 번들 비교는 추정이다.
3. **Preact 11 안정판이 1년 안에 나올 수 있다.** 본 권고는 10.x 잔류를 전제한다.
   10.x가 예상보다 빨리 지원 종료되면 대비책은 §6.2-5(규칙 엔진 프레임워크 무관 분리)다.
4. **Codex의 Svelte 5 오작성률을 정량 측정하지 않았다.** 근거는 커뮤니티 보고와
   "보정 도구가 여럿 존재한다"는 정황이다. 강한 정황이지만 수치는 없다.
5. **인라인 `<symbol>`/`<use>`가 선택될 무료 호스팅의 CSP(콘텐츠 보안 정책)와 충돌하지 않는지**
   확인하지 않았다. 외부 스프라이트 파일 대신 인라인을 쓰면 회피되므로 인라인을 기본으로 한다.
