## 1. 각 선택지 실사

### 1.1 Cloudflare Pages ★ 권고

**무료 한도 (2026-08 확인)**
- **대역폭 무제한** (모든 플랜). 정적 자산 요청은 무료·무제한.
- 빌드 500회/월 (초과 시 Pro $5/mo 필요 — 초과하면 빌드가 안 될 뿐, 사이트는 계속 서비스됨)
- 사이트당 파일 20,000개, 파일 1개당 25 MiB, 저장 10GB
- 커스텀 도메인 무제한 + HTTPS 자동 무료

**초과 시 무슨 일이 일어나는가**
→ **과금되지 않는다.** 무료 플랜에는 overage 청구 항목이 없다. 빌드 500회를 넘기면 그 달 빌드가 거부될 뿐이고, 이미 배포된 사이트는 계속 서빙된다. 즉 "방치 상태에서 트래픽이 튀어도 청구서가 오지 않는다."

**정책 변경 전력 / 1년 방치 리스크**
- 무료 플랜 축소 전력은 사실상 없음(Cloudflare 무료 CDN은 10년 이상 유지).
- **주의 신호 1건**: Cloudflare가 신규 프로젝트를 Workers(Static Assets)로 유도 중이다. 2026년 3월 기준 Workers가 정적 자산·커스텀 도메인에서 Pages와 기능 동등을 달성했고, Cloudflare는 "앞으로 모든 투자·최적화·기능은 Workers에 집중한다"고 공식화했다. **다만 Pages는 deprecated가 아니며 강제 마이그레이션 기한도 발표되지 않았다.** 기존 프로젝트는 계속 동작한다.
- 대응: 지금은 Pages로 시작하되, 마이그레이션이 강제되면 `wrangler.jsonc`에 `assets` 디렉터리를 지정해 Workers로 옮기는 15분짜리 작업이다. 커스텀 도메인은 그대로 승계된다.

**배포 자동화**
- Git 연동(레포 연결 → push하면 Cloudflare가 직접 빌드). **GitHub Actions YAML을 쓰지 않는 것이 이 프로젝트의 정답이다** — 아래 §4 참조(워크플로 파일은 썩는다).

**보너스**: 나중에 WebRTC 시그널링 서버가 필요해질 경우(방 코드 교환), 같은 계정에서 Workers 무료 플랜(10만 요청/일) + Durable Objects(SQLite 백엔드, 무료 플랜 포함, WebSocket Hibernation)로 붙일 수 있다. 이것이 GitHub Pages 대비 Cloudflare의 결정적 우위다. 단, Worker 스크립트를 태우는 요청만 10만/일에 계산되고 정적 자산 요청은 계산되지 않는다.

### 1.2 GitHub Pages ★ 미러로 병행

**무료 한도**
- 소프트 대역폭 100 GB/월, 사이트 1 GB, 빌드 10회/시간
- 커스텀 도메인 + Let's Encrypt HTTPS 무료 (DNS 검증 후 최대 24시간)
- **GitHub Free에서는 public 저장소만** Pages 사용 가능 (private은 Pro 이상)

**초과 시 무슨 일이 일어나는가**
→ **절대 과금되지 않는다.** 소프트 리밋이며 GitHub은 Pages 초과분을 청구하지 않는다. 지속적으로 초과하면 경고 메일 또는 스로틀링. **결제 관계가 존재하지 않으므로 과금 폭탄 확률이 수학적으로 0이다.** 이것이 이 프로젝트 기준에서 가장 강력한 속성이다.

**리스크 (감점 사유)**
- **2026년 GitHub 안정성 악화가 실측되고 있다.** 2026-02-02(Azure 문제로 Actions 성능 저하 → Pages 영향), 02-09, 03-05 대규모 장애. GitHub은 "자체 신뢰성 기준 미달"을 공식 인정했고, 원인으로 "AI 코딩 에이전트가 만드는 완전히 다른 부하 패턴에 맞게 설계되지 않은 아키텍처"를 들었다. 2026-08-06에도 Actions 광범위 장애(Pages 배포 포함). Ghostty 프로젝트(Mitchell Hashimoto)는 2026-04 신뢰성 문제로 GitHub을 떠났다.
- 소스가 public이어야 함(이 프로젝트에선 문제 없음).
- CDN 성능·캐시 제어권이 없음.

### 1.3 Netlify

- 무료 플랜: 월 300 크레딧, **하드 리밋 · 자동 충전 없음 · overage 없음**. 소진 시 사이트가 자동 일시정지.
- **과거 사고**: 2024년 2월, 무료 티어 정적 사이트가 약 190TB 트래픽을 받아 **$104,500 청구서**가 발생. Reddit 1,783 upvote 후 CEO가 면제. 2024년 12월의 단계별 사용량 알림, 크레딧 플랜 도입은 이 사고에 대한 직접적 제품 대응이다.
- 판정: **지금은 안전하다.** 하지만 (a) 2년 사이 과금 모델을 크레딧제로 전면 개편했고 (b) 사고 이전에는 무료 플랜이 초과 시 자동 유료 전환됐다는 사실 자체가 "정책이 바뀌는 회사"라는 증거다. 1년 방치 기준에서 Cloudflare/GitHub보다 뒤진다.

### 1.4 Vercel

- Hobby 무료: 100GB 대역폭, 100만 엣지 요청, 100만 함수 호출. **Hobby에는 overage 옵션이 없어 한도 도달 시 다음 결제주기까지 배포가 정지된다** — 즉 Hobby 자체는 폭탄이 아니다.
- **폭탄은 Pro에서 난다**: Vercel은 하드 스펜딩 리밋을 제공하지 않는다는 것이 오랜 불만이었고, 2025년 1월 한 고객이 엣지 함수 + 이미지 최적화 오설정 조합으로 $380 청구를 맞은 사례가 보고됐다. 2025년 9월 개편으로 Pro에 월 $20 크레딧과 기본 $200 예산 캡(Spend Management)이 붙었다.
- 감점 사유: (a) Hobby는 상업적 이용 금지 — 이 프로젝트는 비상업이라 통과하나 경계가 모호하다 (b) 2025-09 대규모 가격 재편처럼 **정책 변동이 잦다** (c) 정적 사이트에 불필요한 서버리스 계층이 항상 붙어 있다.

### 1.5 Firebase Hosting

- Spark(무료): 저장 10GB, **전송 360 MB/일**. 초과 시 그날은 서빙 중단(과금 아님).
- 360MB/일은 치명적으로 작다. 앱 번들 3MB짜리 PWA면 최초 방문 120명이면 소진이다(SW 캐시 덕에 재방문은 거의 0이지만, 홍보 한 번이면 넘는다).
- **무료 티어 축소 전력 확정**: 2026-02-03부터 Google이 Cloud Storage for Firebase를 표준 GCS 규칙에 맞춰, "Always Free" 범위 안이어도 버킷 생성에 **결제 계정 연결을 요구**하도록 바꿨다. Spark 프로젝트는 콘솔 접근을 잃고 API가 402/403을 반환한다. Hosting 자체는 유지됐지만, **무료 티어에서 기능을 실제로 빼 간 최근 전력**이다. 1년 방치 기준에서 배제.

### 1.6 Surge.sh

- 무료: 대역폭·프로젝트·배포 무제한, `*.surge.sh` 서브도메인에 HTTPS 제공.
- **커스텀 도메인 HTTPS는 유료**(Professional, 약 $30/mo). 리다이렉트·CORS 설정도 유료($10/mo).
- Git 연동 없음(CLI `surge` 한 줄). CI에서 쓰려면 토큰을 넣어야 하고, 그 토큰이 만료/유실되면 조용히 배포가 멈춘다.
- 소규모 운영 주체 = 1년 뒤 존재 여부 리스크. **폴백 후보 이상은 아님.**

### 1.7 itch.io

- HTML5 업로드 지원(zip에 index.html). 하지만 **보안상 사용자 코드를 반드시 iframe으로, `*.itch.zone`이라는 다른 도메인에서 서빙**한다.
- 결과: Service Worker 등록 범위·`beforeinstallprompt`·홈 화면 추가가 정상 동작하지 않는다. **PWA로 쓸 수 없다.**
- 커스텀 도메인은 게임 페이지 수준이며 HTML5 자산 도메인은 통제 불가(itch가 CDN 도메인을 옮길 수 있다고 공지).
- 판정: **호스팅 후보에서 제외.** 다만 "보드게임 모음"이라는 성격상 *발견 채널*로서는 가치가 있으니, 정본 URL로 보내는 링크만 올리는 용도로 쓸 수 있다.

## 2. PWA 설치 · 오프라인 · iOS 저장 정책 (프로젝트 급소)

### 2.1 현재(2026-08) iOS 상태
- **iOS 26부터 홈 화면에 추가한 모든 사이트가 기본적으로 웹앱(standalone)으로 열린다.** 아이콘·전체화면·앱 스위처 등록 모두 정상.
- 푸시 알림: iOS 16.4(2023-03)부터 **홈 화면에 설치된 PWA에 한해** 가능. Safari 18.4의 Declarative Web Push는 SW 없이도 가능. → 이 프로젝트는 푸시가 필요 없다. 무시해도 된다.
- 여전히 불가: 백그라운드 동기화, Web Bluetooth/NFC/USB. → 이 프로젝트는 전부 불필요.
- EU 이슈: Apple이 2024-02 DMA 대응으로 EU에서 홈 화면 웹앱 제거를 예고했다가 **2024-03-01에 철회**했고 iOS 17.4에서 복원했다. 2026년 현재 EU에서도 홈 화면 웹앱은 지원된다(일부 2026년 블로그가 "EU에서 제거됨"이라 쓰고 있으나 이는 철회 이전 정보를 재활용한 오기로 보인다 — 배포 후 EU 사용자 실기기 확인 권장).

### 2.2 7일 삭제 규칙의 정확한 범위 — "기기 안에만 저장" 방침의 급소
- WebKit의 ITP 정책: **Safari에서** 7일간 상호작용이 없으면 스크립트 기록 가능 저장소(IndexedDB, localStorage, sessionStorage, Media keys, **Service Worker 등록 포함**)를 삭제한다.
- **홈 화면 웹앱은 Safari의 일부가 아니므로 자체 "사용일 카운터"를 갖는다.** 웹앱을 실행할 때마다 타이머가 리셋된다. → **설치된 PWA는 7일 규칙에서 사실상 면제된다.**
- **그러나 면제되지 않는 경로가 3개 남는다. 이것이 진짜 위험이다.**
  1. **설치하지 않고 Safari 탭에서만 논 사용자**: 7일 미접속 → 저장한 게임 기록·점수판이 통째로 사라진다.
  2. **Safari "방문 기록 및 웹사이트 데이터 지우기"**: 같은 오리진의 설치된 PWA 저장소까지 함께 삭제된다.
  3. **기기 저장공간 부족 시 OS의 저장소 축출(eviction)** 및 몇 주 이상 미사용 시 캐시/IndexedDB 정리 보고 사례.

### 2.3 그래서 반드시 넣어야 할 설계 (선택 아님)
- **저장 데이터를 "휘발 가능"으로 가정한다.** localStorage/IndexedDB를 유일 사본으로 취급하지 않는다.
- `navigator.storage.persist()`를 호출한다(Chrome/Android에서 지속 저장 승격, iOS에서는 무시되지만 호출 비용 0).
- **내보내기/가져오기를 1급 기능으로 넣는다**: 점수판·저장 게임을 JSON 파일 다운로드 / 파일 선택 복원. 실물 게임 점수판은 사용자에게 유일본이므로 이게 없으면 데이터 손실이 곧 신뢰 상실이다.
- 첫 실행 시 "홈 화면에 추가"를 안내한다(iOS는 `beforeinstallprompt`가 없으므로 iOS 감지 후 공유 버튼 안내 UI를 직접 그린다).
- 앱 안에 "데이터가 사라졌나요?" 안내와 복원 경로를 둔다.

## 3. 업데이트 전파 (SW 캐시 감옥) 와 해법

### 문제
기본 동작상 새 Service Worker는 기존 SW가 제어하는 탭이 전부 닫힐 때까지 `waiting` 상태로 대기한다. 모바일에서 사용자는 탭을 몇 년씩 안 닫는다 → **버그 수정을 배포해도 사용자는 영원히 옛 버전을 본다.** 홈 화면 PWA도 마찬가지다.

### 해법(권장 구성)
1. **HTML(`index.html`, `manifest.json`, `sw.js`)은 network-first + `Cache-Control: no-cache`**. 해시가 붙은 정적 자산(`app.a1b2c3.js`)만 cache-first + immutable.
2. **캐시 이름에 빌드 해시를 넣는다** (`board-v${BUILD_HASH}`). activate에서 다른 이름의 캐시를 전부 삭제.
3. **`skipWaiting()`을 무조건 부르지 않는다.** 새 SW를 감지하면 화면 하단에 "새 버전이 있습니다 · 새로고침" 배너를 띄우고, 사용자가 누르면 `postMessage({type:'SKIP_WAITING'})` → `controllerchange` 이벤트에서 `location.reload()`(1회 가드 플래그로 무한 새로고침 방지).
   - 이유: 무조건 skipWaiting은 열려 있는 옛 페이지가 lazy chunk를 요청할 때 404를 맞아 앱이 죽는다. 게임 도중 화면이 날아가는 것이 이 프로젝트에서 가장 나쁜 실패다.
4. **`registration.update()`를 `visibilitychange`(앱 복귀 시)와 앱 시작 시 호출**한다. 안 하면 브라우저의 갱신 확인 주기에 끌려다닌다.
5. **탈출 해치**: 설정 화면에 "앱 초기화" 버튼 — `getRegistrations()` 전부 `unregister()` + `caches.keys()` 전부 삭제 + 새로고침. 1년 방치 프로젝트에서 사용자가 스스로 벽을 넘을 유일한 수단이다.

## 4. 배포 자동화 — GitHub Actions를 쓸 것인가

**권고: 쓰지 않는다(Cloudflare Git 연동 사용).**

이유는 "유지보수 0"이 최상위 목표이기 때문이다. GitHub Actions 워크플로는 **썩는다**:
- `actions/checkout@v4` 같은 액션 메이저 버전 폐기 공지, Node 런타임 강제 상향(node16→20→24)으로 어느 날 워크플로가 경고 후 실패한다.
- `ubuntu-latest` 이미지 롤오버로 툴체인이 바뀐다.
- 배포용 API 토큰에 만료가 걸려 있으면 **조용히** 배포가 멈춘다.

Cloudflare Pages의 Git 연동은 레포에 YAML을 두지 않는다. push → Cloudflare가 빌드 → 배포. 유지할 파일이 0개다.

**GitHub Pages 미러가 필요하다면** 최소한의 워크플로(`actions/deploy-pages`)를 하나 두되, 실패해도 정본(Cloudflare)에는 영향이 없는 구조로 둔다.

## 5. APK 폴백 — 결론: **만들지 않는다. 웹으로 충분하다.**

### 5.1 "웹만으로는 안 되는 상황"이 실제로 무엇인가
이 프로젝트 요구사항 전체를 훑으면:

| 요구 | 웹(PWA)로 되는가 |
|---|---|
| 홈 화면 아이콘 · 전체화면 | ○ (Android 전면, iOS 26 기본) |
| 오프라인 플레이 | ○ (Service Worker) |
| 한 기기 여러 명 동시 터치 | ○ (Pointer Events, `touch-action: none`) |
| 기기 로컬 저장 | ○ (제약 있음 — §2 참조) |
| 여러 기기 P2P | ○ (WebRTC DataChannel) |
| AI 상대(오목/육목/배틀쉽/요트) | ○ (Web Worker + 필요 시 WASM) |
| 결제/푸시/블루투스/NFC | 전부 **불필요** |

**웹이 못 하는 것 중 이 프로젝트가 필요로 하는 것이 하나도 없다.**

### 5.2 APK가 오히려 유지보수를 만든다 (결정적 근거)
- **Google Play는 매년 target API level 상향을 강제한다.** 미충족 앱은 신규 설치 대상에서 제외되고 결국 사실상 delist 된다. 즉 **Play에 올린 APK는 "1년 방치 가능한 산출물"이 아니다.** 매년 재빌드·재업로드가 필요하다 — 이 프로젝트의 최상위 목표와 정면충돌.
- **서명 키 관리 부담**: 키스토어를 잃으면 그 앱은 영원히 업데이트 불가.
- **개발자 등록비 $25**(1회) + 심사 대기 + 정책 변경 대응.
- **2026년 신규 규제**: Google은 인증된 개발자의 앱만 인증 기기에 설치 가능하도록 전환 중이다. 2025년 10월 일부 개시 → **2026년 3월 전체 개방** → **2026년 9월 30일부터 브라질·인도네시아·싱가포르·태국에서 시행**(이후 확대). 이는 Play뿐 아니라 **사이드로딩(APK 직접 배포)에도 적용된다.** 취미 개발자를 위한 무료 계정 유형이 있으나 **최대 20대 기기 배포 제한**이다. 즉 "APK 파일 던져주기" 경로도 앞으로 자유롭지 않다.

### 5.3 그럼에도 정 필요해지면 (경로만 기록)
- **1순위: PWABuilder → Bubblewrap(TWA).** 내부적으로 Bubblewrap을 쓰며, 기존 PWA URL을 그대로 감싼다. 조건: (a) Lighthouse PWA 80점 이상 (b) **Digital Asset Links(`/.well-known/assetlinks.json`)** 를 사이트 루트에 올려 도메인 소유 검증. 네이티브 API 호출은 불가하지만 이 프로젝트엔 불필요.
- 2순위: Capacitor — 네이티브 플러그인이 필요할 때만. 실측 벤치(Galaxy S24, 2026)에서 TWA 1.2s/60fps vs Capacitor 1.8s/58fps로 TWA가 더 가볍다. 이 프로젝트에 Capacitor를 쓸 이유는 없다.
- **TWA의 대표적 실패**: 앱 안에 URL 주소창이 남는다 → 거의 항상 assetlinks.json의 SHA-256 지문 불일치. Play App Signing이 앱을 **재서명**하므로 로컬 키스토어 지문이 아니라 **Play Console이 제공하는 지문**을 넣어야 한다.

## 6. 권고 구성 (그대로 실행하면 되는 형태)

```
레포: github.com/<user>/boardgames  (public)
 ├─ 정본 호스트: Cloudflare Pages — 레포 Git 연동, 빌드 명령 지정, 자동 배포
 │    └─ 커스텀 도메인(선택): 도메인을 Cloudflare DNS로 이관 후 Pages에 연결, HTTPS 자동
 └─ 미러: GitHub Pages — 최소 워크플로 1개. 정본 장애 시 대체 URL
```

- 도메인은 **있으면 좋고 없어도 된다.** `*.pages.dev`는 HTTPS가 붙어 PWA 설치 요건을 충족한다. 단 도메인이 없으면 나중에 URL을 바꿀 때 사용자의 로컬 저장 데이터가 **오리진 기준으로 전부 사라진다** → 장기적으로는 커스텀 도메인 확보를 권한다(연 $10~15 수준, 이 프로젝트 유일한 유료 항목이 될 수 있음).
- PWA 필수 파일: `manifest.webmanifest`(`display: standalone`, `start_url: "/"`, 192/512 아이콘 + maskable, `theme_color`/`background_color` = 흰색), `sw.js`, iOS용 `apple-touch-icon`.
- 뷰포트: `viewport-fit=cover` + `env(safe-area-inset-*)` 패딩. 폰트 스케일 문제는 `rem` 고정이 아니라 `clamp()`와 `dvh`/`svh` 사용(iOS 주소창 높이 변동 대응).

## 7. 함정 목록 (문서에 안 나오는 실전)

1. **Cloudflare Pages 커스텀 도메인은 그 도메인의 네임서버가 Cloudflare에 있어야 한다.** 외부 DNS에 CNAME만 걸면 검증이 "pending"에서 영원히 안 넘어간다. 특히 apex 도메인.
2. **Cloudflare Pages 파일 20,000개 / 개별 25 MiB 상한.** 기물 이미지·바둑 정석 데이터를 파일 단위로 쪼개 넣으면 배포가 통째로 거부된다. 자산은 스프라이트/번들로 합칠 것.
3. **GitHub Pages + Actions 배포는 `CNAME` 파일을 날린다.** 빌드 산출물에 CNAME이 없으면 커스텀 도메인 설정이 조용히 해제되고 사이트가 `*.github.io`로 되돌아간다. `public/CNAME`을 소스에 커밋할 것.
4. **GitHub Pages는 Jekyll이 `_`로 시작하는 폴더를 무시한다.** SvelteKit(`_app/`), Next(`_next/`) 산출물이 404로 뜬다. `.nojekyll` 빈 파일을 반드시 배포 루트에 둘 것. (Cloudflare는 무관)
5. **레포 서브패스(`/boardgames/`) 배포는 PWA를 조용히 망가뜨린다.** Service Worker 스코프가 서브패스로 제한되고, manifest의 `start_url`이 `/`면 설치 프롬프트가 아예 안 뜨거나 설치 후 빈 화면이 뜬다. 루트 도메인(`user.github.io` 또는 커스텀 도메인)에 배포하거나 base path를 전 경로에 일관 적용할 것.
6. **iOS에서 Safari 탭으로 놀던 사용자가 나중에 홈 화면에 설치하면 진행 데이터가 안 보인다** — 설치된 웹앱과 Safari 탭은 저장소를 공유하지 않는 사례가 반복 보고된다. 첫 방문에 설치를 유도하고, 어긋난 경우를 대비해 내보내기/가져오기를 제공할 것.
7. **iOS "방문 기록 및 웹사이트 데이터 지우기"는 설치된 PWA의 저장소까지 지운다.** 사용자는 이것을 "캐시 정리"로 인식하고 자주 누른다. 점수판 데이터를 유일본으로 두면 안 되는 진짜 이유다.
8. **무조건 `skipWaiting()`은 배포 직후 앱을 죽인다.** 열려 있던 옛 페이지가 요구하는 해시 청크가 새 배포에서 사라져 lazy import가 404 → 게임 도중 흰 화면. 사용자 확인 후 reload 방식으로 갈 것.
9. **과금 폭탄은 무료 티어가 아니라 "한 번 업그레이드를 누른 순간"에 터진다.** Netlify $104,500(2024), Vercel Pro $380(2025-01, 엣지 함수+이미지 최적화 오설정) 모두 유료/자동전환 상태에서 발생했다. 이 프로젝트는 **어떤 호스트에서도 유료 플랜 버튼을 누르지 않는 것**이 유일한 방어선이다. 카드 등록 자체를 하지 말 것.
10. **CI 토큰·GitHub App 인가는 조용히 만료된다.** wrangler API 토큰에 만료일을 넣거나 Cloudflare의 GitHub App 권한이 해제되면 push해도 아무 일이 안 일어나고 에러도 눈에 안 띈다. 만료 없는 토큰을 쓰거나(권장: Git 연동으로 토큰 자체를 없앰), 배포 후 사이트에 표시되는 빌드 해시를 눈으로 확인하는 습관을 둘 것.
11. **TWA 주소창 잔존 = assetlinks.json 지문 불일치.** Play App Signing이 재서명하므로 로컬 키스토어가 아닌 Play Console의 SHA-256을 써야 한다.
12. **Firebase Hosting 360MB/일은 커뮤니티에 링크 한 번 올리면 소진된다.** 초과하면 그날 사이트가 안 뜬다(과금은 안 되지만 서비스가 죽는다).

## 8. 다른 축과 충돌 가능 지점 / 미검증 가정

- **T2(P2P/WebRTC)와의 접점**: 방 코드 교환에 시그널링이 필요하다. "P2P만"이라도 최초 SDP 교환 경로는 필요하며, 선택지는 (a) 수동 코드 복붙/QR (b) 무료 공개 시그널링(수명 불확실) (c) Cloudflare Workers + Durable Objects 무료 티어. (c)를 선택할 가능성이 있다면 호스팅도 Cloudflare로 통일하는 것이 맞다. 이것이 Cloudflare를 1순위로 둔 부수적 근거다. 단 **NAT 통과를 위한 TURN 서버는 무료 선택지가 사실상 없다**(T2 축에서 판단 필요) — 모바일 셀룰러 환경에서 P2P 연결 실패율이 유의미할 수 있다.
- **미검증 1**: 2026년 EU iOS의 홈 화면 웹앱 지원 여부. 2024-03 철회는 확인했으나, 그 이후 재변경이 없었는지는 1차 출처로 확인하지 못했다(일부 2026년 블로그가 "EU 미지원"이라 서술 — 철회 이전 정보 재활용으로 판단하나 실기기 확인 권장).
- **미검증 2**: Cloudflare Pages의 장기 운명. "deprecated 아님 / 강제 마이그레이션 기한 없음"까지는 확인했으나 1년 뒤를 보장할 수 없다. 이 리스크는 GitHub Pages 미러를 병행하는 것으로 완화한다.
- **미검증 3**: 커스텀 도메인 취득 여부는 사용자 결정 사항이다. 도메인 없이 `*.pages.dev`로 가도 전 기능이 동작하지만, 훗날 오리진 변경 시 사용자 로컬 데이터가 전부 소실된다는 비용을 감수하는 것이다.
- **범위 밖**: 빌드 도구·프레임워크 선정(T1 추정), 오프라인 자산 크기 예산, WebRTC 라이브러리 선택은 이 축에서 판정하지 않았다.
