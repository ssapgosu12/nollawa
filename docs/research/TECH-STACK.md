## 0. 이 프로젝트가 지켜야 하는 것 (판정의 기준선)

모든 선택은 아래 순서로 판정했습니다. 위쪽이 이길 때 아래쪽은 양보합니다.

1. **1년 방치해도 계속 돌아간다** — 손대지 않아도 사이트가 뜨고, 게임이 되고, 요금이 안 나온다.
2. **요금 폭탄 경로가 구조적으로 없다** — "실수하면 청구"가 아니라 "실수해도 청구 자체가 불가능"한 곳만 쓴다.
3. **스마트폰·태블릿에서 잘리지 않고 글자 크기 설정이 먹는다** (사용자 명시 필수 요구).
4. **유지보수 인력 0** — 코드를 짜는 것은 LLM 에이전트(Codex)지만, 잘못 짠 것을 발견할 사람이 없다. 그래서 **"조용히 잘못 동작하는" 기술은 성능이 좋아도 탈락**시켰다.
5. 나머지(성능, 개발 편의, 최신성)는 위 4개를 해치지 않는 선에서만.

## 2. 층별 선택 근거

### 2.1 Preact 10 + TSX (화면 렌더링)

**고른 이유**
- Preact는 React(페이스북이 만든 화면 라이브러리)와 거의 같은 문법을 쓰면서 크기가 10분의 1(약 4~5KB)입니다.
- 결정적 근거는 크기가 아니라 **이력**입니다. Preact 10.x는 2019년 10월부터 약 7년간 "메이저 버전 올려라"는 강제가 한 번도 없었고 지금도 패치가 나옵니다(10.29.8 / 2026-08-01). 후보 중 유일합니다.
- Codex(코드를 쓰는 LLM)가 가장 많이 학습한 것이 React 문법인데, Preact는 그 문법의 **움직이지 않는 부분집합**입니다. 오래된 학습 데이터가 오히려 정답이 되는 드문 조합입니다.

**떨어진 것들과 그 이유(요약)**
- **Svelte 5 / SolidJS**: 컴파일은 통과하는데 화면이 조용히 갱신되지 않는 실패 유형이 있습니다. LLM이 구버전 문법을 쓰거나 props를 분해하면 에러 없이 반응성만 죽습니다. **리뷰어가 0명인 이 프로젝트에서 "조용한 오작동"은 최악의 실패**라 탈락.
- **React 19**: 약 2년 주기 강제 변경 이력(16→17 이벤트, 18 개발모드 이중 실행, 19 forwardRef 폐지). 방치 부채가 큽니다.
- **Phaser / PixiJS 게임 엔진**: 350KB~1.2MB에 화면을 그림으로만 그려서 화면 낭독기·키보드 조작이 불가능하고, 손가락으로 확대하면 뿌옇게 번집니다. "흰 바탕 검은 선"에 가장 나쁜 방식.
- **boardgame.io**: npm(패키지 저장소) 마지막 배포가 2022-11-10, 3년 9개월째 정지. 게다가 설치하면 상시 가동 서버 프레임워크(koa, socket.io)가 딸려옵니다. **이미 방치된 라이브러리 위에 "1년 방치 가능한 앱"을 지을 수는 없습니다.** 라이브러리는 버리고 설계 아이디어만 의존성 0으로 모방합니다.

**규율(문서로 못 박음)**: React 생태계 라이브러리는 **하나도** 쓰지 않습니다. 하나라도 쓰면 별칭 설정이 필요해지고, 설정이 반쪽이면 빌드는 통과하고 실행 중에 깨집니다.

### 2.2 인라인 SVG로 6종 보드 전부 통일

바둑 19×19, 오목 15×15, 육목 19×19, 체스 8×8, 배틀쉽 10×10, 요트 주사위 — 전부 SVG입니다.

- **viewBox**(그림 안쪽의 자체 좌표계)를 한 번 정하면, 화면이 360px든 1200px든 브라우저가 알아서 맞춥니다. 화면 크기별 분기 코드가 0줄입니다.
- 스플릿 모드에서 한쪽 화면을 180도 뒤집어도 **터치 좌표 역산 코드가 필요 없습니다**(SVG가 자체 좌표로 이벤트를 줍니다). Canvas(그림판처럼 픽셀을 직접 칠하는 방식)를 골랐다면 부호를 손으로 뒤집어야 하고 반드시 한 번은 틀립니다.
- 화면 낭독기·키보드 조작이 그냥 됩니다(SVG는 문서 구조가 남습니다).

**체스만 CSS Grid가 편한데 왜 SVG로 통일했나** — T1이 제기한 충돌 지점입니다. 판정: **통일**. 근거는 성능이 아니라 **패턴 개수**입니다. 렌더링 방식이 2개면 Codex가 관리할 규칙, 터치 처리, 확대 처리, 회전 처리가 전부 2벌이 되고, 한쪽에서만 고쳐진 버그가 남습니다. 유지보수 인력 0에서 패턴 2벌은 그 자체로 부채입니다.

### 2.3 게임 엔진 = 순수 리듀서 + 액션 로그 (T5 옵션 A)

- **리듀서**란 "현재 판 + 한 수 → 다음 판"을 돌려주는 함수 하나를 말합니다. 이 함수는 화면 라이브러리를 전혀 모릅니다(import 0).
- 공통으로 정하는 계약은 5개(`init`/`reduce`/`seatsToAct`/`terminal`/`redact`)뿐, 약 40줄입니다.
- **`legalMoves`(둘 수 있는 수 목록)를 공통 계약에서 뺀 것이 핵심**입니다. 이걸 필수로 넣으면 요트·배틀쉽·파티게임·점수판이 전부 "빈 껍데기 구현"을 갖게 되고, 그 순간 공통층이 게임을 삼키기 시작합니다. 필요한 게임만 선택적으로 구현합니다.
- **`redact`**는 "이 좌석에게 보여 줄 판"을 만드는 함수입니다. 배틀쉽에서 상대 함대 위치를 지우는 데 씁니다.
- **공통층 예산 820줄**을 문서에 명시합니다. 넘기 시작하면 추상화가 게임을 삼키는 신호입니다.

버린 대안: 만능 인터페이스 하나로 20개 통일(요트에서 무너짐), 게임 20개 완전 독립(같은 버그를 20번 만듦), CRDT(자동 병합은 보드게임 규칙을 파괴함 — 같은 칸에 둘 다 두는 게 "정상 동작"이 됨).

### 2.4 멀티 통신 = Cloudflare Durable Objects 릴레이 (가장 큰 판정)

용어부터:
- **P2P**(peer-to-peer): 서버를 거치지 않고 기기끼리 직접 통신.
- **WebRTC**: 브라우저끼리 P2P 연결을 맺는 웹 표준.
- **시그널링**: WebRTC 연결을 맺기 *전에* 서로의 접속 정보를 교환해 주는 중개 단계. **이건 P2P로 할 수 없어서 어차피 누군가의 서버가 필요합니다.**
- **NAT / CGNAT**: 여러 사용자가 공인 IP 하나를 나눠 쓰는 구조. 이동통신(LTE/5G)이 대표적이고, 이 경우 P2P 직결이 실패합니다.
- **TURN**: P2P 직결이 실패했을 때 트래픽을 대신 중계해 주는 서버. 즉 **TURN을 쓰는 순간 그 연결은 이미 P2P가 아닙니다.**
- **Durable Objects(DO)**: Cloudflare가 제공하는 "이름을 부르면 그 이름 전용 작은 서버 객체가 자동으로 생기는" 서비스. 놀고 있으면 잠들고(hibernation), 요청이 오면 깨어납니다.

**판정: WebRTC를 버리고 Cloudflare Workers + Durable Objects WebSocket 릴레이를 쓴다.**

근거를 순서대로:

1. **P2P의 유일한 이점이 이 프로젝트에는 없습니다.** 보드게임 통신량은 시간당 300KB 미만입니다. 절약할 대역폭이 0인데 그 대가로 연결 협상 코드 전부를 떠안습니다.
2. **"P2P를 쓰면 서버가 없다"는 전제가 거짓입니다.** 시그널링 서버가 어차피 필요하고, 한국 이동통신 환경에서는 상당수가 TURN(=중계 서버)으로 떨어집니다. 즉 P2P를 골라도 서버는 2개(시그널링 + TURN) 필요하고, 릴레이를 고르면 1개면 됩니다.
3. **남의 무료 인프라에 얹는 순간 1년 방치가 깨집니다.** PeerJS 공개 브로커는 공식 이슈 제목이 그대로 "Public server is unreliable"이고, Trystero가 쓰는 공개 Nostr 릴레이는 개인·커뮤니티 운영이라 수시로 사라집니다. 무료 TURN 자격증명은 **최대 48시간 만에 만료**됩니다 — 배포 이틀 뒤 아무 로그 없이 전원 연결 실패가 나는데, 고칠 사람이 없습니다.
4. **릴레이만이 "방의 주인"을 가집니다.** 스마트폰은 화면이 꺼지면 연결이 끊깁니다(보드게임에서는 상시 발생). 릴레이는 방 상태를 들고 있어서 재접속 = 소켓 다시 열기로 끝납니다. P2P는 방 주인이 나가면 판이 사라지고, 그걸 살리려면 분산 합의 코드를 써야 합니다.
5. **요금 폭탄 경로가 없습니다.** Cloudflare 무료 플랜은 한도 초과 시 **청구가 아니라 에러**를 돌려줍니다. 하루 10만 요청 · 받은 WebSocket 메시지는 20개당 1요청으로 계산되어 실질 하루 200만 메시지이고, 보드게임은 한도의 1%도 못 씁니다.

**헌장 문구와의 관계**: 프로젝트 제약에 "멀티는 방 코드 P2P(WebRTC)만"이라고 적혀 있습니다. 그 문장의 실제 의도는 **"랜덤 매칭·랭킹·로그인·개인정보 DB를 만들지 마라"**로 읽었고, DO 릴레이는 그 의도를 전부 만족합니다(계정 없음, 방 코드만, 개인정보 저장 없음, 빈 방은 24시간 뒤 자동 삭제). 다만 **문구 자체와는 다른 선택이므로 사용자 확인이 필요합니다** — §9 결정 대기 1번.

**보험**: 전송층을 `Transport` 인터페이스(`connect`/`send`/`onMessage`/`onPeerChange`, 약 50줄) 뒤에 숨깁니다. Cloudflare가 정책을 바꾸면 파일 하나를 Trystero 어댑터로 교체합니다. **단, 두 경로를 동시에 살려두지 않습니다**(둘 다 썩습니다). 어댑터는 잠들어 있는 대체품이지 상시 폴백이 아닙니다.

### 2.5 권위 모델 — 서버에 게임 규칙을 올리지 않는다

릴레이를 쓰면 "서버가 규칙을 검증하게 할까?"라는 유혹이 생깁니다. **거절합니다.**

- 규칙을 서버에 올리면 배포 대상이 2개(웹앱 + 워커)가 되고, 둘의 버전이 어긋나면 진단 불가능한 버그가 납니다.
- 랭킹도 낯선 사람도 없으므로 부정행위를 막을 실익이 0입니다.

**확정 구조**: DO는 ①좌석 목록과 접속 순서 ②최신 판 스냅샷(JSON 약 1.5KB)과 순번(seq)만 들고, 규칙은 모릅니다. 접속 순서상 첫 번째 클라이언트가 "권위 좌석"이 되어 수를 검증·적용하고 **판 전체를 통째로** 올리며, DO가 그걸 저장하고 전원에게 뿌립니다. 권위 좌석이 나가면 DO가 다음 접속자를 지목합니다(서버가 유일한 심판이므로 판단이 갈릴 여지가 없습니다).

**왜 "수 목록"이 아니라 "판 전체"를 보내나** — 이것이 T5의 핵심 발견입니다. 수 목록만 보내고 각자 재현하는 방식(lockstep)은 양쪽이 **완전히 같은 버전**일 때만 맞습니다. 그런데 오프라인 캐시(서비스워커) 때문에 A는 구버전, B는 신버전을 도는 상황이 **정상적으로** 발생합니다. 그러면 에러 없이 두 화면이 다른 판이 되고, 며칠 뒤 "가끔 게임이 이상해져요"라는 재현 불가 버그로 돌아옵니다. 판 전체를 보내면 게스트는 계산을 안 하므로 이 실패 자체가 사라집니다. 1.5KB짜리를 아끼려고 이 위험을 살 이유가 없습니다.

**추가 안전장치**: 접속할 때 빌드 해시(그 배포의 고유 번호)를 교환하고, 다르면 "새 버전이 있습니다. 새로고침하세요"를 띄웁니다.

### 2.6 저장 = IndexedDB + 내보내기

- **localStorage 금지.** iOS Safari는 7일간 안 쓰면 지웁니다. 주 1회 미만으로 하는 보드게임 앱에서 진행 중인 판과 점수 기록이 통째로 사라집니다.
- IndexedDB를 쓰고 첫 실행에 `navigator.storage.persist()`(이 사이트 데이터를 함부로 지우지 말아 달라는 요청)를 호출합니다.
- 저장 시점은 `visibilitychange`(화면 가림)와 `pagehide`만 씁니다. `beforeunload`/`unload`는 모바일에서 상당수 발화하지 않아 "껐다 켜니 판이 날아감"이 됩니다.
- **실물 게임 점수판처럼 다른 곳에 없는 기록은 반드시 내보내기/가져오기(JSON 파일)를 제공합니다.** iOS의 "방문 기록 및 웹사이트 데이터 지우기"는 설치된 앱의 데이터까지 지우는데, 사용자는 그걸 단순 캐시 정리로 알고 자주 누릅니다.

### 2.7 AI 상대

- 오목: 미니맥스 + 위협 탐색, 깊이 4 수준. 육목은 탐색 공간이 커서 미니맥스를 포기하고 위협 기반 탐욕 알고리즘으로.
- 요트: 1단계 전방 탐색(킵 조합 32 × 확률표) — 1ms 미만.
- 배틀쉽: 확률 밀도 탐색 — 워커도 필요 없는 수준.
- 체스·바둑 AI는 **만들지 않습니다**(사용자 제약).
- Web Worker 설정 주의: Vite에서 `worker.format`을 `'iife'`로 내려야 합니다. 기본값(`module`)은 일부 안드로이드 내장 브라우저에서 **에러 없이 조용히 로드 실패**해 AI가 영원히 응답하지 않습니다.
- iOS는 백그라운드 탭의 워커를 종료시킵니다. **모든 AI 요청에 타임아웃 + 단순 폴백**을 답니다. 이게 없으면 화면 전환 한 번에 AI 차례에서 게임이 영구히 멈춥니다.

방 목록을 담는 데이터베이스가 없습니다. **방 코드가 곧 객체 이름**이라, 코드를 부르면 그 방이 생기고 아무도 안 쓰면 사라집니다.

### 3.2 메시지 흐름 (한 수를 두는 과정)

```
1. 폰 C가 "여기에 둔다"를 터치
   C ──{move, seq기대값}──> DO
2. DO가 권위 좌석(A)에게 전달
   DO ──{move}──> A
3. A가 순수 리듀서로 규칙 검증 + 적용
   반칙이면 → {reject, 사유}만 C에게
4. A가 새 판 전체를 올림
   A ──{snapshot, seq+1, buildHash}──> DO
5. DO가 저장하고 전원에게 방송 (좌석별로 redact 적용)
   DO ──{snapshot}──> A, B, C
6. B와 C는 계산하지 않고 그대로 그림
```

```
[재접속]   폰 C 화면 꺼짐 → 소켓 끊김 → 다시 켬 → 소켓 열기
           DO ──{snapshot(최신), seq}──> C     … 끝. 복구 코드 없음.

[권위 이탈] A가 나감 → DO가 감지 → 접속 순서상 다음인 B를 권위로 지목
           DO ──{youAreAuthority, snapshot}──> B    … 판은 안 멈춤.

[유령 접속] 앱 레벨 하트비트(20초마다 핑) 없으면 iOS에서
           "접속 중"으로 남은 채 영원히 상대 턴을 기다린다. → 하트비트 필수.
```

### 3.3 통신량 점검

바둑 한 판(약 250수) 기준: 올라가는 메시지 250(수) + 250(스냅샷) = 500개.
Cloudflare는 받은 메시지 20개를 1요청으로 계산 → **25요청**. 하루 한도 10만 요청.
즉 **하루에 바둑 4,000판**을 둬야 한도에 닿습니다.

## 4. 반응형·색 설계 규칙 (실제 CSS)

### 4.1 용어

- **뷰포트**: 브라우저에서 웹페이지가 실제로 보이는 사각형 영역.
- **`100vh`**: 화면 높이 100%. **문제는 이 값이 모바일 주소창을 포함한 높이라는 것**입니다 → 아래가 잘립니다.
- **`100svh`**(small viewport height): 주소창·툴바가 **다 보일 때**의 높이. 언제나 안전한 최소값이라 절대 잘리지 않습니다. → **이걸 씁니다.**
- **`100dvh`**(dynamic): 실시간으로 변하는 높이. 값이 계속 바뀌어 판이 미세하게 커졌다 작아지고, 그때 손가락 아래 교차점이 움직여 오착수가 납니다. → **보드에는 쓰지 않습니다.**
- **safe area**: 아이폰 노치(카메라 홈)와 홈 인디케이터가 가리는 영역.
- **컨테이너 쿼리**: "화면 크기"가 아니라 "이 요소 자신의 크기"에 따라 스타일을 바꾸는 기능. 스플릿 모드에서 반쪽이 된 보드에 특히 유용합니다.

### 4.2 최소 리셋 (직접 작성 — 리셋 라이브러리 금지)

```css
/* normalize.css / Tailwind preflight를 복붙하지 않는다.
   그것들은 -webkit-text-size-adjust:100% 를 자동으로 넣는데,
   그 한 줄이 안드로이드의 "글자 크기" 접근성 설정 반영을 죽인다.
   우리는 viewport 메타로 자동 확대를 막고, 설정 반영은 살려 둔다. */

*, *::before, *::after { box-sizing: border-box; }

body {
  margin: 0;
  background: #fff;
  color: #000;
  font-family: system-ui, -apple-system, "Segoe UI", "Noto Sans KR", sans-serif;
  -webkit-tap-highlight-color: transparent;
}

button, input, select, textarea { font: inherit; color: inherit; }
svg, img { display: block; max-width: 100%; }
```

HTML `<head>`에 반드시:

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
<!-- viewport-fit=cover: 노치 영역까지 화면을 쓰되, 아래 CSS의 env()로 안전 여백을 준다 -->

<meta name="color-scheme" content="only light">
<!-- 이걸 빼면 안드로이드 크롬의 자동 다크 모드가 페이지를 임의로 어둡게 칠해
     "흰 바탕 + 검은 선"이 지켜지지 않는다. 다크 모드를 "안 만든다"는 선택지는
     실제로 존재하지 않으며, 명시적으로 차단해야만 흰 바탕이 유지된다. -->
```

`user-scalable=no`는 **넣지 않습니다**. iOS는 무시하고 안드로이드에서만 저시력 사용자의 확대를 막는 순손실이기 때문입니다.

### 4.3 앱 셸 — 잘림을 구조적으로 없애는 뼈대

```css
:root {
  --pad: 0.75rem;
  /* clamp(최소, 선호, 최대). 선호값에 rem을 반드시 섞는다.
     vw만 쓰면 사용자가 브라우저를 200% 확대해도 글자가 커지지 않는다
     (vw는 확대에 반응하지 않음) — 겉보기엔 반응형인데 접근성이 죽는 함정. */
  --ui:    clamp(0.875rem, 0.80rem + 0.55vw, 1.15rem);
  --title: clamp(1.15rem,  1.00rem + 1.20vw, 1.75rem);
}

.app {
  height: 100svh;              /* 주소창이 어떤 상태여도 절대 잘리지 않는 높이 */
  display: flex;
  flex-direction: column;
  overflow: hidden;            /* 셸 자체는 스크롤하지 않는다 */
  padding:
    env(safe-area-inset-top)    env(safe-area-inset-right)
    env(safe-area-inset-bottom) env(safe-area-inset-left);
  /* env()로만 쓴다. JS로 한 번 읽어 저장하면 반드시 틀린다 —
     iOS는 툴바가 보일 때 하단 값을 0, 접히면 34px로 실시간으로 바꾼다. */
}

/* ★ 이 min-height:0 이 없으면 100svh를 정확히 써도 아래가 잘린다.
   flex 자식의 기본값 min-height:auto가 "내용보다 작아지지 마라"로 동작해
   컨테이너가 화면 밖으로 밀려나기 때문. 잘림 사고의 압도적 1위 원인이며,
   증상이 '뷰포트 단위 문제'처럼 보여 엉뚱한 곳을 몇 시간 고치게 만든다. */
.app > .content { flex: 1 1 auto; min-height: 0; display: flex; }

/* 게임 목록·설정·방 코드 입력처럼 내용이 길어질 수 있는 화면은
   셸 전체가 아니라 이 영역만 스크롤한다. */
.scroll { flex: 1 1 auto; min-height: 0; overflow-y: auto; padding: var(--pad); }
```

### 4.6 플레이어 4색 — 색만으로는 절대 구분되지 않는다

```css
:root {
  --p1: #A87400;  /* 노랑(호박) 흰 바탕 대비 약 4.1:1 */
  --p2: #D32F2F;  /* 빨강              약 5.0:1 */
  --p3: #2E7D32;  /* 초록              약 5.1:1 */
  --p4: #1565C0;  /* 파랑              약 5.8:1 */
}
```

순수 노랑(`#FFFF00`)은 흰 바탕 대비가 1.07:1이라 **어떤 방법으로도 기준을 넘길 수 없어** 어둡게 조정했습니다.

**그런데도 색만으로는 안 됩니다.** 위 4색의 상대 휘도(밝기)는 빨강 0.161 · 초록 0.155로 사실상 동일합니다. 즉 흑백으로 인쇄하면 같은 회색이고, 적색약(빨강을 잘 못 보는 색각 특성) 시뮬레이션에서 빨강과 초록의 색 차이가 사실상 0으로 붕괴합니다. **이건 색을 고르는 문제로 해결되지 않습니다.**

**확정 규칙 — 플레이어 표시는 항상 3중 부호화:**

| | 색 | 모양 | 번호 |
|---|---|---|---|
| P1 | 노랑 | ● 원 | 1 |
| P2 | 빨강 | ■ 사각 | 2 |
| P3 | 초록 | ▲ 삼각 | 3 |
| P4 | 파랑 | ◆ 마름모 | 4 |

모든 말·마커·점수판 행에 **검은 외곽선 + 모양 + 번호**를 함께 넣습니다. 색은 "빨리 알아보게 해 주는 보조 신호"이지 정보의 유일한 전달 수단이 아닙니다.

### 4.7 스플릿 모드(화면 반을 뒤집는 모드)의 구조 규칙

```css
.seat--flipped { transform: rotate(180deg); }
```

이 한 줄에 딸린 규칙 3개를 **구조로 못 박습니다**:

1. **토스트·모달·드롭다운은 회전 영역 안에 렌더링 금지.** 회전이 걸린 조상은 `position: fixed` 자손의 기준 상자가 되어 팝업이 거꾸로 뜹니다. 이건 버그가 아니라 명세라 영원히 안 고쳐집니다. → 오버레이는 반드시 `.app` 직속에 그립니다.
2. **회전 영역 안에 `<select>`·텍스트 입력·날짜 선택기 금지.** 키보드와 확대경이 전부 정방향으로 떠서 사용자가 목을 꺾습니다. 점수판 화면이 정확히 이 함정에 걸립니다 → 입력은 정방향 영역에서만.
3. **회전 영역은 스크롤 금지**(스크롤 방향이 반대가 됩니다).

### 4.8 방 코드 입력창

```css
.room-code-input {
  font-size: 1.05rem;   /* 절대 16px 미만으로 내리지 말 것 */
  text-transform: uppercase;
  letter-spacing: 0.2em;
}
```

16px 미만이면 iOS가 포커스 시 화면을 자동 확대하고, 입력을 마쳐도 원래 배율로 돌아오지 않습니다(2026년에도 그대로).

## 5. 배포 파이프라인

### 5.1 구조

```
로컬 작업
  │  npm ci --ignore-scripts     (lockfile 그대로 설치 + 설치 스크립트 차단)
  │  npm run build               → dist/
  │  git add dist/  ← 빌드 결과물을 저장소에 커밋한다 (의도적)
  │  git push
  ▼
GitHub 저장소 (공개)
  ├─ Cloudflare Pages: Git 연동으로 자동 빌드·배포        [정본]
  │     빌드 명령: npm ci && npm run build / 출력: dist
  └─ GitHub Pages: git subtree push --prefix dist origin gh-pages   [미러]
        (수동 1줄. 워크플로 YAML 파일을 만들지 않는다)

릴레이 (거의 안 바뀜)
  relay/ 에서  npx wrangler deploy   ← 최초 1회 + 드물게
```

**GitHub Actions(자동 실행 스크립트) YAML을 쓰지 않는 이유**: 그 파일은 액션 메이저 버전 폐기와 Node 런타임 강제 상향으로 1~2년 안에 썩습니다. 그리고 썩으면 조용히 멈춥니다. Cloudflare Git 연동은 우리가 유지할 파일이 0개입니다.

**`dist/`를 커밋하는 이유**: 1년 뒤 빌드 도구가 깨져도 사이트는 계속 삽니다. 이게 이 프로젝트의 가장 값싼 보험입니다.

### 5.2 반드시 지킬 설정

| 항목 | 값 | 이유 |
|---|---|---|
| `package.json` 버전 | **캐럿(`^`) 제거, 정확 버전 고정** | 1년 뒤 `npm install`이 다른 의존성 트리를 설치해 빌드가 깨지는 게 방치 프로젝트 사망 1위 원인 |
| lockfile | 반드시 커밋 | 위와 같은 이유 |
| 설치 명령 | `npm ci --ignore-scripts` | 2025년 npm 자가전파 웜(Shai-Hulud)이 설치 훅을 악용해 1,300개+ 패키지 버전을 감염시킴. 의존성 최소화는 취향이 아니라 보안 요구 |
| `vite.config.ts` | **15줄 이하 유지** | 설정 옵션이 적을수록 개명·폐기에 맞을 확률이 낮음. Vite 8은 실제로 `rollupOptions`를 개명했다 |
| Node 버전 | `.nvmrc`에 기록 | Vite 8이 Node 20.19+를 요구하는 식의 상향이 반복됨 |
| 빌드 해시 | 화면 구석에 표시 | 배포 연동이 조용히 끊겨도 눈으로 즉시 알아챈다 |
| `base` | `'./'` (상대 경로) | 정본과 미러의 경로 깊이가 달라도 같은 빌드가 양쪽에서 동작 |
| `worker.format` | `'iife'` | 안드로이드 내장 브라우저에서 워커가 조용히 로드 실패하는 것 방지 |

### 5.3 서비스워커 정책 (오프라인 + 업데이트)

**서비스워커**란 브라우저에 상주하면서 네트워크 요청을 가로채 캐시로 응답할 수 있는 스크립트입니다. PWA(Progressive Web App — 홈 화면에 설치되고 오프라인에서도 도는 웹앱)를 오프라인으로 돌게 하는 물건인데, **잘못 걸면 사용자가 영원히 옛 버전에 갇힙니다.**

확정 정책 3줄:
1. **HTML은 network-first** — 네트워크를 먼저 시도하고 실패할 때만 캐시.
2. **파일명에 해시가 붙은 자산(JS/CSS)만 cache-first** — 이름이 바뀌면 새 파일이므로 안전.
3. **무조건 `skipWaiting()` 호출 금지.** 열려 있던 옛 페이지가 요구하는 조각이 새 배포에 없어서 게임 도중 흰 화면이 됩니다. 대신 **"새 버전이 있습니다" 배너 → 사용자가 누르면 교체 → 1회 가드 후 새로고침**.

**배포 전 실기기 검증(필수)**: 구버전 설치 → 새로 배포 → 새로고침 2회 → 신버전 확인.

|---|---|---|---|
| 1 | **Cloudflare 무료 티어 축소 / DO 유료화** — 멀티가 통째로 죽음 | 방 입장이 안 되고 릴레이가 오류 반환 · 대시보드에 결제 요구 배너 · 정책 변경 메일 | `Transport` 어댑터 파일 1개를 Trystero(P2P)로 교체(약 반나절). 단일기기·점수판·AI 모드는 전혀 영향 없음 |
| 2 | **iOS가 로컬 저장을 지움** — 점수 기록과 진행 중인 판 소실 | 앱 시작 시 `navigator.storage.persisted()`가 false로 기록됨 · 사용자가 "기록이 사라졌다" | IndexedDB + `persist()` + **설치 유도** + 중요한 기록은 JSON 내보내기 상시 안내. 점수판은 판 종료 시 자동으로 내보내기 제안 |

| 4 | **npm 공급망 공격** — 개발 PC와 토큰 탈취 | 설치 로그에 낯선 스크립트 · GitHub에서 모르는 저장소 생성 알림 · 토큰 유출 경고 메일 | 직접 의존성 4개 유지 · `--ignore-scripts` 상시 · 의존성 자동 업데이트 자동병합 금지 |

| 6 | **DO 하이버네이션 오사용** — 빈 방이 무료 한도를 하루 만에 태움 | Cloudflare 대시보드의 duration(GB-s) 급증 · 릴레이가 한도 초과 오류 | `ws.accept()` 금지, **반드시 `state.acceptWebSocket(ws)`** · 방 상태는 예외 없이 `state.storage`에 저장 · alarm으로 빈 방 24시간 뒤 삭제 · 사용량 알림 설정 |
| 7 | **배포 연동이 조용히 끊김** — push해도 아무 일도 안 일어나고 에러도 없음 | 빌드 해시가 안 바뀜(이 신호가 없으면 몇 달을 모른다) | 빌드 해시 상시 표시 · 정본/미러 이중화 · 토큰 만료일 없는 연동 사용 |
| 8 | **유령 접속** — 상대가 오지 않는 턴을 영원히 기다림, "가끔 멀티가 안 돼요"로 신고됨 | 접속자 목록에 있는데 20초 넘게 응답 없음 | 앱 레벨 하트비트(20초) + 60초 무응답 시 좌석 이탈 처리 + 권위 재지정. `readyState === OPEN`을 절대 신뢰하지 않는다 |

**표에 없지만 기록해 둘 것**: 요금 폭탄은 무료 티어에서 터지지 않고 **"업그레이드 버튼을 누른 순간"** 터집니다(Netlify 2024년 $104,500, Vercel 2025년 $380 사례 모두 유료 상태에서 발생). 이 프로젝트의 유일하고 확실한 방어선은 **어느 호스트에도 결제수단을 등록하지 않는 것**입니다.

## 7. APK 판정

### 결론: **만들지 않는다. 웹(PWA)으로 충분하다.**

요구사항을 하나씩 대조한 결과입니다.

| 요구 | 웹으로 되나 | 방법 |
|---|---|---|
| 홈 화면 아이콘으로 실행 | ✅ | PWA 설치(manifest) |
| 인터넷 없이 실행 | ✅ | 서비스워커 캐시 |
| 기록을 기기에 저장 | ✅ | IndexedDB |
| 여러 기기 멀티 | ✅ | WebSocket 릴레이 |
| 한 기기 여러 명 동시 터치 | ✅ | Pointer Events(브라우저 표준 다중 터치) |
| 화면 잘림 없음 | ✅ | `100svh` + `env(safe-area-inset-*)` |
| 계정 없음 | ✅ | 애초에 만들지 않음 |

**즉 이 프로젝트가 요구한 것 중 웹이 못 하는 것이 하나도 없습니다.**

그리고 APK는 "최후 폴백"으로서도 값이 나쁩니다:
- Google Play는 **매년 target API 레벨 상향을 강제**합니다. 즉 Play에 올린 APK는 정의상 **1년 방치가 불가능한 산출물**입니다 — 이 프로젝트의 최상위 목표와 정면으로 충돌합니다.
- Play 밖 설치(사이드로딩)도 자유롭지 않게 바뀌는 중입니다. Google은 인증된 개발자의 앱만 인증 기기에 설치되도록 전환 중이고(2026-09-30부터 일부 국가 시행 후 확대), 취미 개발자용 무료 경로는 배포 기기 수가 제한됩니다.
- 웹뷰 래핑(TWA)을 만들면 앱 안에 주소창이 남는 증상이 흔한데, 원인은 거의 항상 서명 지문 불일치입니다. 고칠 사람이 없는 프로젝트에 새 고장 지점을 하나 더 만드는 셈입니다.

### APK를 다시 검토해야 하는 구체적 조건 (이 중 하나가 실제로 발생했을 때만)

1. **안드로이드 사용자들이 "홈 화면에 추가"를 못 찾는 일이 반복될 때** — 설치 안내 UI를 개선해도 실패하면 안드로이드 전용 TWA를 검토. (iOS는 어차피 APK가 무의미하므로 이 조건은 안드로이드 한정입니다.)
2. **서버 없이 같은 와이파이의 기기를 자동으로 찾아 붙는 기능이 요구로 추가될 때** — 블루투스·로컬 네트워크 직접 탐색은 웹에서 불가능합니다. (현재 요구에는 없습니다. 방 코드 입력으로 충분합니다.)
3. **화면 방향 강제 잠금이 필수 요구가 될 때** — iOS는 2026년에도 웹에서 방향 잠금을 지원하지 않습니다. 다만 그때도 해법은 APK가 아니라 **"가로·세로 양쪽을 다 지원하는 설계"**이며, 실제로 그렇게 설계합니다.
4. **저장 데이터 소실이 실사용에서 반복되고 내보내기로 감당이 안 될 때** — 단, 이 경우에도 iOS는 APK로 해결되지 않으므로 안드로이드에서만 부분 해결입니다.

**즉 1번을 제외하면 APK는 문제를 풀지 못합니다.** 현시점 판정은 명확히 "만들지 않음"입니다.

조사로 답할 수 있는 것은 이미 답했습니다. 아래 3개만 **실물 기기에서 30분** 안에 확인하면 설계 가정이 확정됩니다.

1. **저가 안드로이드 폰에서 361교차점 SVG 바둑판의 착수 반응 속도.** (노드 수는 여유롭지만 "매 수마다 얼마나 다시 그리는가"가 진짜 변수입니다. 격자는 `path` 1개, 돌은 바뀐 것만 갱신하는 구조로 만들고 측정.)

3. **아이폰에서 홈 화면 설치 후 `navigator.storage.persisted()` 값과, 화면 잠금 후 재접속 복구.**

## 9. 사용자 결정 대기 항목

아래는 **조사로 답할 수 없고 사용자가 정해야만 진행되는 것**들입니다.

1. **[가장 중요] 헌장의 "멀티는 방 코드 P2P(WebRTC)만"을 Cloudflare 릴레이로 재해석하는 것을 승인하는가?**
   - 권고: **승인.** WebRTC를 고르면 (a) 시그널링 서버가 어차피 필요하고 (b) 이동통신에서 상당수가 중계 서버로 떨어지며 (c) 무료 중계 서버 자격증명이 48시간마다 만료되어 **"1년 방치"가 구조적으로 불가능**합니다.
   - 승인 시 필요한 것: Cloudflare 계정 1개, `wrangler deploy` 1회, **결제수단 미등록**.
   - 거부 시: Trystero(공개 릴레이 이용 P2P)로 가고, 대신 "공개 릴레이가 사라지면 멀티가 죽는다"를 상시 위험으로 안고 갑니다. 앱 코드는 `Transport` 인터페이스 덕에 거의 바뀌지 않습니다.

2. **저장소를 공개(public)로 할 것인가?** GitHub 무료 계정은 공개 저장소에서만 GitHub Pages를 쓸 수 있습니다. 비공개를 원하면 미러(2차 방어선)를 포기하거나 다른 미러를 찾아야 합니다.

3. **직접 도메인을 살 것인가(연 1~2만 원)?** 단순 취향 문제가 아닙니다. 브라우저 저장은 **주소(오리진) 단위**라, 나중에 주소를 바꾸면 사용자의 저장된 판과 점수 기록이 **전부 사라집니다**. 즉 도메인 확보는 데이터 보존 정책의 일부입니다. 사지 않으면 `*.pages.dev` 주소를 영구히 씁니다(기능은 전부 동일).

4. **다크 모드를 제공할 것인가?** "흰 바탕 + 검은 선" 지시와 충돌할 수 있어 확인이 필요합니다. 제공하지 않기로 해도 `color-scheme: only light` 선언은 **반드시** 넣습니다(안 넣으면 안드로이드가 임의로 어둡게 칠합니다).

5. **파티 게임의 정확한 목록과 성격.** 종류·인원·동시 입력 여부·여러 기기 멀티 지원 여부가 미정입니다. 특히 **카드 게임(비공개 손패 + 섞기)이 포함되는지**가 중요합니다 — 포함되면 "비공개 정보는 가리기만 하면 된다"는 설계 판정을 다시 봐야 합니다.

6. **한 방의 최대 인원(좌석 수 상한).** 4명인지 8명인지에 따라 좌석 UI와 스플릿 레이아웃 설계가 달라집니다.

7. **오목·육목 AI의 기대 강도.** "창피하지 않은 수준"은 주관적 기준이라 착수 전에 눈높이를 고정해야 합니다(예: "초보자를 이기면 충분" vs "3목·4목 함정을 볼 줄 알아야 함"). 육목은 오목보다 탐색이 훨씬 어려워 같은 기준을 적용하면 개발량이 크게 늘어납니다.

8. **점수판 데이터의 자동 내보내기 강도.** 판이 끝날 때마다 파일 저장을 제안할지(안전하지만 성가심), 아니면 설정에서 수동으로만 할지(편하지만 소실 위험). 실물 게임 기록은 다른 곳에 사본이 없으므로 이 결정이 실제 데이터 소실 여부를 가릅니다.

  (JSON으로 바꿀 때 `Set`은 조용히 `{}`로 증발합니다. 바둑 활로 추적이나 배틀쉽 명중 칸에 가장 쓰고 싶은 자료형이라 반드시 걸립니다)
- 화면 구석 빌드 해시 표시
- 체스 perft 테스트(정답표 대조: 시작 위치 깊이4 = 197,281 / 깊이5 = 4,865,609)

  (없으면 6개월 안에 테스트가 전부 무시 처리되어 죽습니다 — **있는데 안 도는 테스트는 없는 것보다 나쁩니다**)
