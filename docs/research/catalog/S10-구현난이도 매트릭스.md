# S10 — 구현난이도 매트릭스 (구현 비용 대비 가치)

조사일: 2026-08-12 · 축: S10 · 방법: 웹 검색 + 실측 산정
전제: 프로젝트 제약(웹 PWA / 공용·스플릿·멀티(P2P 방코드)·점수판 4모드 / 무서버·무DB·무계정 / 흰바탕+검은선, 색은 플레이어 1~4 구분에만 / 스마트폰 세로 성립 / 유지보수 최소)

용어(이 문서에서 처음 나오는 것):
- **규칙 엔진**: 합법수 생성·승패 판정·특수 규칙 처리를 담당하는 순수 로직 계층. UI와 분리되며 테스트 가능한 부분.
- **사석(死石) 마킹**: 바둑 종국 후, 반상에 남아 있지만 죽은 것으로 합의된 돌을 지정하는 절차. 계가의 전제 조건.
- **세키(seki, 빅)**: 양쪽 말이 서로 잡지 못한 채 공존하는 형태. 일본·한국 룰에서 그 안의 공배는 집으로 세지 않는다.
- **금수(禁手)**: 렌주(오목 정식룰)에서 흑에게만 금지된 착점(삼삼·사사·장목).
- **TURN 서버**: WebRTC에서 P2P 직결이 실패했을 때 트래픽을 중계해 주는 서버. STUN(공인 주소 확인)과 달리 실제 데이터가 통과한다 = 대역폭 비용 발생.
- **impl_difficulty 척도**: 1=하루, 3=며칠, 5=주 단위. 규칙 엔진 + UI + 3모드 배선 + 테스트 + AI(해당 시)를 **전부 포함한 정직 견적**. 낙관 금지.

## 1. 확정 코어 6종 정직 산정

### 1-1. 체스 — impl 4
**규칙 엔진.** 직접 구현하면 함정 밀도가 최고다. 캐슬링은 킹이 **지나가는 칸**까지 공격받지 않아야 하고(킹은 공격받는 칸을 통과할 수 없다), 앙파상은 **두 폰이 같은 행에서 동시에 사라지므로 수평 핀 전용 검사**가 따로 필요하다 — 체스 프로그래밍 위키가 "핀, 특히 앙파상이 얽힌 핀이 주된 난점"이라고 명시하는 지점이다. 3수 반복은 기물 배치만이 아니라 **수순권·캐슬링 권리·앙파상 권리까지 같아야** 동일 국면으로 센다(그래서 위치 해시에 그 비트들을 넣어야 한다). 여기에 스테일메이트, 50수 규칙, 기물 부족 무승부.

**비용 절감 결론:** `chess.js`(MIT, TypeScript, 헤드리스, 합법수 생성·체크메이트·무승부 판정 내장, 브라우저 검증됨)를 쓰면 엔진 난이도가 4→1로 떨어진다. 정적 호스팅에 번들만 얹으면 되므로 무서버 제약에 위배되지 않는다. **직접 구현은 명확한 낭비다.**

**화면.** 8×8은 폰 세로에서 편안하다(360px 폭 → 칸 45px, 터치 타깃 기준 44px 충족). 흰바탕/검은선 제약과도 궁합이 좋다 — 기물은 채움(P1)/외곽선(P2)으로 구분하면 색 없이 성립한다.

**네트워크.** 상태 전체가 FEN 문자열 한 줄(<90바이트). P2P 데이터채널로 국면 전체를 매 수 보내도 무해하다 = **역직렬화만으로 desync 복구가 되는 유일한 코어**. 재접속 처리가 가장 싼 게임.

**AI.** 여기가 진짜 비용이다. "쉬운 AI"라도 랜덤 합법수는 즉시 들통나 재미가 없고, 쓸 만하려면 알파베타 + 정지탐색(quiescence) + 기물/위치 평가표가 필요하다. chess.js 위에 깊이 3~4가 현실적 상한(라이브러리 수 생성이 비트보드 엔진보다 느리다). 목표를 "초심자에게 지지 않을 정도"로 낮춰 잡아도 며칠. → 종합 **impl 4**.

### 1-2. 바둑 — impl 5 (§3에서 별도 심화)

### 1-3. 오목 — impl 2 (자유룰+스왑) / 4 (렌주 금수)
**규칙 엔진.** 자유룰은 마지막 착점에서 4방향만 훑으면 끝 — 반나절. 그런데 **한국에서 통용되는 "정식 오목"은 렌주룰이고, 흑 금수(삼삼·사사·장목) 판정은 난이도가 한 단계가 아니라 두 단계 뛴다.** 금수 정의가 재귀적이기 때문이다: "삼"은 열린 넉동으로 발전할 수 있는 형태를 뜻하고, 그 발전 지점이 **그 자체로 금수라면 삼으로 치지 않는다**. 실전에는 3×3×3, 4×4×3, 4×3×3, 4×4×4×4 같은 다중 포크가 존재하며(renju.net 상급 튜토리얼), 오픈소스 렌주 엔진 mintaka가 "strict rule implementation"을 **기능으로 광고**한다는 사실 자체가 이게 공짜가 아니라는 증거다.

**최대 레버(이 조사의 최고 가성비 결론):** 렌주 금수 대신 **스왑 오프닝**을 채택하라. "흑이 첫 수를 두면 백이 색을 바꿀 권리를 갖는다"(중국권에서 널리 쓰이는 swap-after-1st-move)는 **10줄이면 구현되고 선수 이점을 실질적으로 해소한다.** 금수 판정기 며칠 + 영구 버그 리스크를 10줄로 대체한다. 금수는 "고급 옵션"으로 후순위 백로그.

**화면.** 15×15는 폰 세로에서 칸 24px — 직접 탭은 아슬아슬하다. **탭 → 미리보기 → 확정** 2단 착수를 넣으면 성립한다(이 컴포넌트는 이후 육목·바둑이 전부 재사용한다).

**AI.** 카탈로그 전체에서 **AI 가성비 1위**. 열린3/닫힌3/열린4 패턴 점수표 + 기존 돌 주변 후보만 보는 깊이 2~4 알파베타면 캐주얼 상대를 이긴다. 200줄 수준.

### 1-4. 육목(Connect6) — impl 2
**규칙 엔진이 오목보다 오히려 단순하다.** 흑이 첫 수 1개, 이후 양측이 매 턴 2개씩, 6개 이상 연속이면 승. 2003년 우이첸(I-Chen Wu) 고안 시점부터 "턴당 2수가 선수 이점을 구조적으로 상쇄"하도록 설계됐다 → **금수 규칙 자체가 필요 없다.** 장목(6목 초과)도 그냥 승리로 처리하므로 예외 분기가 없다.

**실제 비용은 UI에 있다:** 2개를 놓고 확정 전에 하나만 무르는 상호작용, 그리고 "지금 몇 번째 돌인가" 표시. 그리고 19×19가 표준 판(바둑판을 그대로 쓰는 것이 가장 편하다는 게 통설)이라 **바둑과 같은 화면 문제를 상속한다** → 15×15 옵션을 기본값으로 두는 것을 권한다.

**AI.** 오목보다 확실히 어렵다. 한 턴의 착수 조합이 최대 C(361,2) ≈ 6.5만 → 순진한 미니맥스는 죽는다. 현실 해법은 "돌 하나씩 탐욕적 위협 점수로 순차 배치". 약하지만 놀 만하다.

**재사용 이득이 결정적:** 오목을 먼저 만들면 격자 렌더러·2단 착수·연속 판정·위협 패턴표를 그대로 상속받아 실질 **반나절~하루**.

### 1-5. 배틀쉽 — impl 3
**규칙 엔진은 카탈로그 최하 난이도**(배치 겹침 검사 + 명중 판정 + 격침 판정). 문제는 규칙이 아니라 **정보 은닉**이다.

- **공용(shared) 모드의 구조적 마찰:** 한 기기에 양쪽 함대가 다 있다. 배치 단계마다 "P2에게 넘기세요 → 준비되면 탭" 인계 화면이 필요하고, 사격 후에도 화면이 바뀌어야 한다. 흘끗 보는 것을 막을 방법은 없다(신뢰 기반). 이 인계 플로우 자체가 하나의 기능이다.
- **스플릿(split) 모드는 원리적으로 불가능.** 한 화면을 나눠 각자 보면 상대 함대가 노출된다. → 배틀쉽의 modes에서 split은 빼야 한다.
- **멀티(P2P)가 본진.** 다만 무서버 P2P에서는 각 클라이언트가 자기 함대를 들고 명중/빗나감을 **스스로 정직하게 답한다** = 마음먹으면 거짓말이 가능하다. 방 코드로 아는 사람끼리 노는 용도이므로 수용 가능. (커밋-리빌 해시로 막을 수 있지만 제약 대비 과투자.)

**AI 가성비 2위.** 헌트/타깃 + 패리티(체스판처럼 격자를 반만 훑어도 최소 크기 배가 반드시 걸린다)는 수십 줄로 평균 65수, 확률밀도까지 얹으면 50% 게임을 ~42수에 끝낸다(DataGenetics). **적은 코드로 "생각하는 것처럼 보이는" 봇**을 얻는 유일한 코어.

**화면.** 10×10 두 판을 폰 세로에 동시에 못 넣는다 → "내 바다 / 적 바다" 탭 전환 + 미니맵. 표준적이지만 공짜는 아니다.

### 1-6. 요트 다이스 — impl 3
**규칙 엔진.** 점수 함수 13개는 순수 함수라 테스트가 쉽다. 함정은 보너스 계층: 상단 63점 → 35점 보너스, 요트 추가 달성 시 100점, 그리고 **조커 규칙**(요트칸이 이미 채워졌을 때 같은 눈의 상단 칸 강제 → 없으면 하단 사용, 단 풀하우스/스몰·라지 스트레이트는 정상 판정). 게다가 **퍼블리셔 공식 문서 자체가 연도별로 오락가락한다** — 즉 "정답"이 없다.

**비용 절감 결론:** 원조 **요트(Yacht)**는 12개 카테고리, 상단 보너스 없음, 조커 없음이다. **한 변형을 골라 문서에 고정하고 그걸로 끝내라.** 조커 규칙 클래스를 통째로 삭제하면 impl 3 → 2.

**화면이 오히려 최대 난관이다.** 13행 × 4플레이어 = 52셀 + 주사위 5개 + 리롤 컨트롤을 360px 폭에 넣어야 한다. 해법은 (a) 열 가로 스크롤 또는 (b) "현재 플레이어 1명 전체 + 나머지 요약" 뷰. **이 표 레이아웃 자산이 그대로 (d) 점수판 모드의 뼈대가 된다** — 그래서 요트를 점수판 모드보다 먼저 만드는 것이 이득이다.

**네트워크.** 주사위 RNG 권한 문제(누가 굴리나)가 유일한 설계 결정. 방장 권한으로 고정하면 끝.
**모드 적합.** 공용·점수판 양쪽에 완벽하고, **스플릿이 실제로 자연스러운 유일한 코어**(태블릿을 가운데 놓고 좌/우 각자 점수표, 중앙에 공용 주사위).

## 2. 초기 확장 후보 (제약을 실제로 통과한 것만)

- **커넥트4(사목)** — 7×6, 중력 애니메이션, 승리판정은 오목 코드의 5→4 치환. 폰 세로 최적. 깊이 7 알파베타가 즉답. **impl 1 / fit 5.** 이름만 "사목"으로 갈 것(§4 상표).
- **리버시** — 8방향 뒤집기 + "합법수 없으면 패스"라는 단 하나의 예외. **흑/백 돌이 흰바탕+검은선 팔레트 그 자체**라 색 제약에서 감점이 0인 몇 안 되는 게임. 코너 가중 평가 미니맥스가 깊이 5~6에서 꽤 강하다. **impl 2 / fit 5.**
- **도트앤박스** — 점과 선만으로 성립 = **팔레트 제약에 가장 완벽하게 맞는 게임**. 완성한 상자를 플레이어 색으로 칠하는 것이 4색 규칙의 정확한 용처. 격자 크기를 화면에 맞춰 5×5~8×8로 조절 가능(폰/태블릿 양쪽 성립). 2~4인. **impl 2 / fit 5.** 단 제대로 된 AI(체인·패리티 이론)는 의외로 어렵다 → 탐욕 봇으로 시작.
- **범용 점수판** — 실물 보드게임의 기록 담당. 라운드×플레이어 표, +1/+5/+10 버튼, 라운드별 이력, 되돌리기. 앱스토어 리뷰에서 실제로 요청된 기능이 "라운드별 전체 이력을 되돌아보고 싶다"였다. **콘텐츠 유지보수 0, 서버 0, 모드 (d)의 유일한 입주자.** impl 2 / fit 5.
- **체커** — 8×8이라 화면은 최상. 함정은 **강제 잡기 + 연속 점프 분기 선택 UI**, 그리고 변형 난립(영국식 8×8 vs 국제식 10×10 나는킹). 한 변형 고정 필수. **impl 3 / fit 4.**
- **쿼리도** — 선화 친화, 2~4인, 상태 작음. 벽을 놓을 때마다 **모든 말의 도착 경로 존재 여부를 BFS로 검사**해야 하는 것이 유일한 진짜 알고리즘. 9×9 + 벽 홈은 폰에서 밀도가 높다. **impl 3 / fit 4.**

### 탈락 사례 (왜 안 되는지 남긴다)
- **코드네임류 단어게임 — fit 1.** 구현 자체는 어렵지 않다(impl 3). 탈락 이유가 전부 제약 쪽이다: ①25단어 카드 풀을 **계속 채워 넣어야 함** = 유지보수 최소화 위배 ②스파이마스터만 정답표를 봐야 하는데 공용 기기에서 성립 불가, 스플릿으로도 불가 → **기기 2대 강제** ③이름·아트가 상표. 이 항목은 "impl이 낮아도 fit이 죽이면 탈락"의 표본이다.
- **카탄류 자원경영 — fit 1.** 자원 5종+개발카드+도로/마을/도시+항구를 흰바탕/4색으로 표현 불가(색이 정보를 나른다 = 명시적 감점 대상), 육각 대형 보드는 폰 세로에서 붕괴, 실시간 교역 협상은 P2P 상태 동기화 난이도를 한 단계 올린다. impl 5 / fit 1.

## 3. 바둑 심화 — 집 계산과 종국 판정 (요구된 별도 논의)

바둑을 "돌 놓고 따내면 끝"으로 견적 내면 **실제 비용의 절반 이하**가 나온다. 어려운 곳은 대국이 아니라 **대국이 끝난 다음**이다.

### 3-1. 쉬운 부분 (반나절~하루)
착수, 활로 계산(flood fill), 따냄, 자살수 금지, 단순 패(직전 국면 해시 1개와 비교). 이건 정말 쉽다. 슈퍼코(동형반복 금지)는 전체 이력 해시 집합이 필요해 한 단계 위지만 여전히 관리 가능하다. 삼패·장생 같은 순환은 "무승부 처리"로 도피할 수 있다.

### 3-2. 진짜 벽 ①: 사석 판정은 자동화가 **불가능**하다
종국 시 반상의 죽은 돌을 골라내는 것 — 이건 알고리즘 문제가 아니라 **탐색 문제**다. 강한 엔진 없이는 풀리지 않고, 심지어 **아주 강한 인간 기사들끼리도 사활 판정에서 이견이 갈린다**(Online Go Forum "Are those stones dead or is it seki?"). 최종 국면이 아닌 중간 국면에는 단순 해법이 아예 없고, 최종 국면에서도 까다롭다는 것이 이 분야의 공통 인식이다.

→ 따라서 **자동 판정을 포기하고 합의 UI를 만들어야 한다.** 이것이 상태 기계 하나를 통째로 추가한다:

```
대국중 --2연속 패스--> 사석마킹 --양측 동의--> 계가 --> 결과
                          |                      
                          +--이견/취소--> 대국 재개 (누가 두는가? 마킹 초기화?)
```

이 "마킹 → 동의 → 이견 시 재개" 루프가 **바둑 구현 공수의 절반**이며, 견적에서 가장 흔히 누락되는 항목이다. 게다가 세 모드에 각각 배선해야 한다: 공용(한 기기에서 두 사람이 번갈아 동의), P2P(양측 동의 상태 동기화 + 한쪽 이탈 처리).

### 3-3. 진짜 벽 ②: 세키
일본·한국식 territory 계가에서 **세키 안의 집은 세지 않는다.** 세키 자동 판정은 별도 알고리즘이며, 오픈소스 구현 `lightvector/goscorer`(세키 감지 포함 territory scoring)의 저자 본인이 구현을 "quite tricky"라고 표현한다. 더 중요한 것은 **그 라이브러리조차 "사석이 올바르게 마킹되어 있고 필요한 보강수가 두어져 있을 때"만 정확하다**는 점이다 — 즉 §3-2의 문제를 대신 풀어 주지 않는다. 라이브러리는 계가만 해결하고, 마킹 UI는 여전히 우리 몫이다.

### 3-4. 계가 방식 선택 = 최대 비용 절감 지점
| | 중국식(area: 돌+집) | 한국·일본식(territory: 집−사석) |
|---|---|---|
| 사석 마킹 필요 | 필요(합의) | 필요(합의) |
| 세키 예외 | 사실상 없음 | **있음(세키 집 불산입)** |
| 사석 카운트 | 불필요 | 필요(포로 수 추적 + 되메움 개념) |
| 산술 복잡도 | 낮음 | 중간 |
| 덤 | 7.5 | 6.5 |

**권고: MVP는 중국식.** 승패 결과는 거의 항상 일치하며, 세키 예외 처리와 포로 회계 두 덩어리를 통째로 없앤다. 한국 사용자는 "집 계산"에 익숙하므로 UI에서 "중국식 계가(돌+집)" 라벨과 한 줄 설명을 반드시 붙일 것.

### 3-5. 화면 — 19×19는 폰 세로에서 정직하게 말해 성립하지 않는다
360 CSS px 폭에서 19선이면 교점 간격 ≈ 18px, 돌 지름 ≈ 17px. 권장 터치 타깃(≈44px)의 40% 수준이다. 커뮤니티가 폰에서 9×9·13×13을 권하는 이유이고, 실제 상용 앱이 릴리스 노트에 "작은 폰에서 19×19 표시 수정"을 올리는 이유다.
필수 처치: **핀치 줌 + 팬 + 손가락 위 확대 루페 + 탭→확정 2단 착수.** 이건 바둑 전용 비용이 아니라 육목·오목 19로에도 재사용되므로 공용 컴포넌트로 만들 것.

### 3-6. 바둑 AI
넣지 마라. 약한 봇은 눈 개념이 없어 자기 집을 메우며 자살하고, 몬테카를로를 돌리면 폰에서 느리다. **바둑의 modes에서 solo_ai는 제외**가 정직한 결론이다.

### 3-7. 바둑 MVP 정의 (권고)
9×9 + 중국식 계가 + 수동 사석 마킹 + 2연속 패스 종료 + 단순 패. 그 다음 13×13 → 19×19(루페) → (선택) 한국식 계가 옵션.

## 4. 상표·저작권 위험 (규칙은 자유, 이름은 아니다)
게임 **규칙 자체는 저작권 대상이 아니지만 이름·아트는 상표다.** 실무 처리:
- Connect Four → **"사목"** / Othello → **"리버시"** / Yahtzee → **"요트 다이스"** / Battleship → 일반명 "해전" 병기 / Quoridor → 자체 명칭. 체스·바둑·오목·육목·체커·도트앤박스는 명칭 위험 없음.
- 아이콘·기물 아트는 전부 자체 선화로 그린다(팔레트 제약상 어차피 그래야 한다).

## 5. 네트워크 공통 위험 (모든 멀티 게임에 균등 적용)
방 코드 P2P는 시그널링 서버(초경량, 무상태)와 STUN이 필요하고, **NAT 홀펀칭은 약 90%만 성공한다** — 나머지는 TURN 중계가 필요하다. 즉 "완전 무서버"는 실제로 **연결 성공률 ~90% 서비스**를 의미한다. 대응: ①턴제 게임이므로 실패 시 "공용 모드로 전환하세요" 폴백 안내 ②전 게임의 상태를 **작은 전체 스냅샷으로 매 턴 전송**해 desync·재접속을 무료로 해결(체스 FEN, 바둑 좌표열, 요트 점수표 전체 — 전부 1KB 미만). 이 설계는 게임별 델타 동기화 코드를 아예 없앤다.

## 6. 모드 적합성에서 나온 반직관적 결론
**(b) 스플릿 모드가 실제로 성립하는 게임이 거의 없다.** 추상 보드게임은 두 사람이 같은 판 전체를 봐야 하므로 화면 분할이 무의미하고(태블릿을 가운데 두는 shared + 상대 방향 180° 회전 옵션이 정답), 정보 은닉 게임(배틀쉽)은 분할하면 은닉이 깨진다. 스플릿이 자연스러운 곳은 **각자 독립된 개인 영역을 동시에 갖는 경우** 뿐 — 즉 **요트 다이스(좌/우 개인 점수표 + 중앙 공용 주사위)와 개인 점수판**이다. 스플릿을 전 게임 공통 기능으로 설계하면 대부분 빈 껍데기가 된다. → 스플릿은 "점수표 계열 전용 기능"으로 좁혀 잡을 것.

## 7. 만들어야 할 순서 (근거 포함)

**Phase 0 — 게임이 아니라 자산 (첫 게임에 묻어서 만들되 처음부터 공용 모듈)**
반응형 SVG 격자 렌더러 / 턴 상태기 + 되돌리기 / **탭→미리보기→확정 2단 착수** / 180° 회전 옵션 / localStorage 이어하기 / 공용 모드 인계 화면.

**1. 오목 (자유룰 + 스왑 오프닝)** — 확정 코어이면서 위 자산 전부를 최초로 만든다. 육목·바둑·커넥트4가 이 코드를 상속한다. 금수는 넣지 않는다(스왑으로 대체).
**2. 커넥트4(사목)** — 오목 승리판정 재사용으로 반나절. **초기 라인업 수를 가장 싸게 늘린다.**
**3. 육목** — 오목 자산 90% 재사용, 규칙은 더 단순. 하루.
**4. 리버시** — 8×8 격자 + 미니맥스 뼈대를 도입한다. 이 알파베타 골격이 6번 체스 AI로 이어진다.
**5. 요트 다이스** — 격자와 완전히 다른 축(점수표 UI + 4인 지원 + 스플릿)을 개척한다. **이 표 레이아웃이 곧 점수판 모드다.**
**6. 범용 점수판** — 5번의 파생물로 사실상 무료. 모드 (d) 개통.
**7. 배틀쉽** — 은닉 정보 인계 플로우 + 2보드 전환을 만든다. **P2P를 여기서 처음 도입**한다(그 전까지는 공용 모드로 충분하고, 연결 실패 10% 리스크를 한 게임에 격리해 검증할 수 있다). 값싼 좋은 AI 보너스.
**8. 체스** — chess.js 도입, UI가 무겁다(드래그/승격 다이얼로그/기보/무승부 사유 표시/AI).
**9. 바둑** — 9×9부터. 사석 마킹 합의 상태 기계와 루페를 마지막에 붙인다. **가장 늦게** 시작하는 것이 옳다: 다른 8개가 만들어 둔 격자·확대·인계·P2P 자산을 전부 물려받는 유일한 게임이고, 혼자서는 주 단위를 먹는다.
**10+.** 도트앤박스 → 체커 → 쿼리도.

**이 순서의 원칙:** ①확정 코어 중 자산을 만드는 것부터 ②각 단계가 다음 단계 비용을 낮추는 순서 ③리스크(P2P·바둑 계가·체스 AI)는 자산이 쌓인 뒤에 ④"싼 게임을 먼저"가 아니라 **"싸면서 다음 것을 싸게 만드는 게임을 먼저"**.
